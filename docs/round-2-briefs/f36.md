# F-36 — `domains:reconcile` throws uncaught in production every three hours

**Audit text:** *"`F-36` `domains:reconcile` throws uncaught in production every
three hours."*

Traced read-only on `claude/relaxed-turing-nh8ybf` at `d822de0`. **Confirmed, to
the line, with the mechanism established.**

## The mechanism, end to end

`app/Console/Commands/ReconcileDomains.php:37`:

```php
foreach (DomainRegistrarFactory::drivers() as $driver) {
    $orphans += $reconcile->findOrphans($driver);
}
```

`DomainRegistrarFactory::drivers()` (`:46-49`) is a **hardcoded list**:

```php
return [FakeDomainRegistrarProvider::NAME, SyRegistryProvider::NAME];
```

`make('fake')` (`:63`) does `new FakeDomainRegistrarProvider`, whose constructor
(`:112-117`) opens with:

```php
FakeRegistrarGuard::assertNotProduction(self::NAME);
```

The loop has no `try`/`catch`. `handle()` has no `try`/`catch`. The schedule
entry (`routes/console.php:351-355`, cron `35 */3 * * *`, `withoutOverlapping`,
`onOneServer`, `appendOutputTo`) has no `onFailure`. In production the command
therefore throws, eight times a day, at :35.

The production guard is working exactly as designed. The defect is that a
scheduled command walks a driver list that always contains the fake.

## Two things the audit's one line does not say, and both matter

**1. It throws *after* the reconciliation has already succeeded.** `handle()`
runs `$reconcile->execute(...)` at `:26` and prints its summary at `:28` before
the orphan loop is reached. So the sweep's actual work — settling `indeterminate`
registrations, which is the other half of the Timeout Rule and the reason this
command exists at all — lands. Only the orphan scan dies, and it dies on the
first driver.

This is the worst available failure shape, not the most benign one: a scheduled
task that fails *every single run* while doing most of its job. An operator who
sees `domains:reconcile` red at 02:35, checks, finds the domains settled, and
concludes it is noise, is behaving reasonably. The alert is then dead, and the
run where reconciliation genuinely fails looks identical to the eight hundred
before it.

State this in the round's reproduction. A round that only proves "it throws"
has proved the smaller half.

**2. `ReconcileDomains.php:37` is the only site in the repository that
instantiates every driver in the list.** I checked (`grep -rn "::drivers()"`
over `src app routes tests`): the other five call sites use `drivers()` for
error-message text (`UnknownXDriverException::named($driver, self::drivers())`)
or to list names in `ProviderRegistryServiceProvider:228-236`, and two are
assertions in `tests/Feature/Security/ProductionGuardTest.php:371-372`. Nothing
else constructs from it. **The blast radius is one loop**, which bounds the
round — do not let it become a factory refactor.

## The fix is a decision, not a patch

Three candidate shapes, and the round must argue for one rather than reach for
the nearest:

1. **Skip drivers that refuse to exist here.** Catch the guard's exception
   per driver and continue. Cheapest; also silently swallows a *real* driver
   that cannot construct, which is the failure you most want to see.
2. **Derive the driver set from configuration** rather than hardcoding it, so
   production never names the fake. Correct, larger, and touches a factory
   shared by four modules — check the cross-branch matrix before starting.
3. **Ask each driver whether it is available in this environment** before
   constructing it, which is the only one of the three that distinguishes "not
   configured here" from "broken".

Whichever is chosen: the scheduled entry should also carry a failure path, so
that the next thing that throws in this command is visible as an incident
rather than as a line in `storage/logs/schedule.log`.

## Proof obligations

- **First-fail:** a test that runs the command with the application in
  production and shows the throw — red before, green after. The existing
  production-guard tests assert the guard fires; they do not assert that a
  scheduled command survives it.
- **Do not weaken `FakeRegistrarGuard`.** The guard is correct. A round that
  makes the fake constructible in production to fix a console command has
  inverted the finding, and §27 covers it.
- Nothing here touches `REAL_REGISTRAR_VERIFIED`, which stays `NONE`. The
  command is read-only towards registries by design and must remain so.
