# F-22 — Critical drift is invisible on every channel

Round-1 audit, line 224, OPERABILITY:

> Critical drift is invisible on every channel: the metric is unalerted, the
> listener only writes `Log::error`, the log path Alloy ships is not the path
> Laravel writes, and the Loki ruler is wired to Alertmanager with zero rule
> files and no rules directory mounted.

I traced all four claims read-only before writing this. **All four are true**,
two of them are stronger than the audit states, and there is a fifth thing the
audit does not mention. What follows is what I measured, so you can start from
evidence rather than from a search. Re-measure anything you intend to write
down — my trace is a starting point, not a citation.

## What is actually there

### 1. The metric is unalerted — and the omission is specific, not general

Two drift metrics are emitted:

    lynomia_open_drift_total        ProductCollector.php:569
    lynomia_resource_drift_open     ProvisioningCollector.php:109

`grep -rn 'drift' infrastructure/monitoring/prometheus/rules/` returns
**nothing**. But this is not a stack without rules: there are **65 `alert:`
rules** across six files, referencing **28 distinct `lynomia_*` metrics**
(backups, MRR, IP runway, queue depth, failed jobs, node capacity, webhooks,
and more). So the framing that matters is not *"nobody wrote alert rules"* but
**"drift was left out of a mechanism that covers twenty-eight other series"**.
That is a sharper finding and it points at a smaller fix.

### 2. The listener writes one `Log::error` and nothing else

`src/Modules/Provisioning/Application/Listeners/AlertOnCriticalDrift.php`.
It early-returns on any severity but `Critical`, then writes one `Log::error`
with `drift_id`, `provider`, `resource_type`, `kind`, `service_id`,
`provider_reference`. No notification, no metric increment, no queue.

Its docblock is thoughtful and mostly right — it explains why it is not queued
(one log line must not be lost behind an unhealthy queue) and why only Critical
logs at error (so an orphan on a hand-operated node does not page at 3am).
**Read it before you change anything.** Both reasons are good and a fix that
tramples them is worse than the finding.

### 3. Alloy reads a path nothing writes — and the directory does not exist

    Alloy    __path__ = "/var/log/lynomia/lynomia.json"   (alloy/config.alloy:46)
    Laravel  storage_path('logs/lynomia.json')            (config/logging.php:67)

`grep -rn '/var/log/lynomia' infrastructure/` returns exactly two hits: Alloy's
read path, and the compose file mounting that same directory read-only into the
container. **Nothing in the repository creates it, symlinks it, populates it or
rotates into it.** No Ansible task, no deploy script, no logrotate rule. So the
audit's "is not the path Laravel writes" understates it: the shipped path is not
a path at all.

And the log line does reach `lynomia.json`: `default` is `stack`, `LOG_STACK`
defaults to `structured`, and `structured` is the JSON channel at
`storage_path('logs/lynomia.json')`. So the listener writes successfully into a
file nothing ships.

**The fifth thing, and it is a defect under this programme's own standard.**
The `structured` channel's docblock says, in the repository, as a statement of
fact:

> Grafana Alloy tails this file and ships it to Loki.

It does not. That is a false sentence in the tree, of exactly the kind this
programme treats as a defect in its own right — and it is the sentence that
would stop a reader from discovering the gap.

### 4. The Loki ruler is wired up and has nothing to evaluate

`loki/loki-config.yml`:

    ruler:
      storage: { type: local, local: { directory: /loki/rules } }
      rule_path: /loki/rules-temp
      alertmanager_url: http://alertmanager:9093
      enable_api: true

`infrastructure/monitoring/loki/` contains **one file**, `loki-config.yml`.
There is no `rules/` directory anywhere for Loki, and the compose service mounts
only the config plus the named volume `loki-data:/loki` — so `/loki/rules`
resolves inside an empty volume. Zero rule files, no rules directory mounted,
Alertmanager wired. Claim confirmed as written.

Note `enable_api: true`: rules *could* be pushed at runtime. Nothing in the
repository does. Decide whether a fix should ship files or use the API, and say
why — do not leave it implied.

### Where an alert would go if one existed

`alertmanager.yml` already routes: `severity = critical` → `pagerduty-critical`,
with sub-routes for backups and payments; `severity = warning` →
`platform-team`; a monitoring-team route; and inhibition rules. The file states
deliberately that there is no muted or low-priority receiver, because "an alert
nobody..." (read the full sentence at line 20).

So the delivery half exists and works. This finding is about the four links
between a drift row and that routing tree, every one of which is broken.

## What the round has to do

The four breaks are independent and each alone is sufficient to silence drift.
Fix all four or say why one is out of scope — do not fix the visible one and
leave the chain broken.

1. **Alert rules for the drift metrics.** They belong beside the twenty-eight
   others, in the file whose subject matches. Match the existing rules' shape:
   read several of them first and follow their conventions for `for:`,
   labels, `summary`/`description`, and runbook annotations. Get the severity
   right — `lynomia_resource_drift_open` and `lynomia_open_drift_total` are not
   the same thing and may not deserve the same treatment.
2. **The log path.** Either Alloy reads where Laravel writes, or the deployment
   creates the path Alloy reads. Both are defensible; pick one, implement it
   where it actually runs (the Ansible monitoring role deploys Alloy to each
   application host with the same `config.alloy`), and **correct the false
   sentence in `config/logging.php`** either way.
3. **The Loki ruler.** Either ship rule files and mount them, or remove the
   ruler wiring. A ruler pointed at an empty directory and an Alertmanager is
   worse than no ruler: it looks configured. If you keep it, the rules must be
   derivable from what the structured log actually contains — which you can only
   know after (2).
4. **The listener.** Judge whether one `Log::error` is the right contract once
   the chain works. It may be: if the metric alerts and the log ships, the log
   line is evidence rather than the alarm, and the docblock's reasoning about
   not queueing still holds. If you conclude the listener is fine as it stands,
   **say so as a finding with the argument**, do not quietly leave it.

## Standing constraints

- **Do not contact real infrastructure.** Do not run Prometheus, Loki, Alloy,
  Alertmanager or Docker against anything, do not push to a real Alertmanager,
  do not deploy. This finding is entirely configuration and code in the tree.
- What you *can* do is validate syntax locally if a validator is available
  offline (`promtool check rules` if the binary exists — check, do not install),
  and otherwise pin the shape with a test that parses the YAML and asserts
  structure. A rule file nobody can parse is the same class of defect as an
  unmounted rules directory.
- **Pin it, do not just write it.** This programme's standard is that a fix
  which no test can distinguish from its absence is not a fix. Ask what test
  fails if someone deletes your alert rule, unmounts the rules directory again,
  or changes the log path back. Write that test.
- Do not edit `docs/round-2-remediation-ledger.md`; read it at
  `/home/user/cloud/docs/round-2-remediation-ledger.md`. Put what you want
  recorded in your hand-back.
- Three proofs for any band: JSON with no `skipped` key and `tests == passed`;
  `--log-junit` with every `testsuite` at `skipped="0"`; `ARTISAN-TEST EXIT=0`.
- Quote counts, never assertion totals, and name the instrument and the
  invocation shape in the same sentence.
- F-39 is the other Observability finding and the audit groups them:
  *"Collectors are correct; the rules were never written."* Read F-39's row in
  the ledger before you start so the two rounds do not collide, and say in your
  hand-back if you touch anything F-39 will need.

## One thing to be careful about

The tempting shortcut is to write an alert rule, see YAML on disk, and call the
chain fixed. Three of the four breaks are invisible to anyone reading only the
file they changed. Before you report, trace the whole path yourself — drift row
→ metric → scrape → rule → Alertmanager route → receiver, and separately drift
row → event → listener → log file → Alloy → Loki → ruler → Alertmanager — and
say for each hop what you verified and how.
