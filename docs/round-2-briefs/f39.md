# F-39 — fifteen alert names appear in runbooks and in no rule file

file."* — OPERABILITY.

## The measurement, and how to reproduce it

64 alerts are defined across the seven files in
`infrastructure/monitoring/prometheus/rules/` (`^\s*-\s*alert:\s*(\S+)`).
Extracting every backtick-quoted CamelCase token of eight or more characters
from `docs/runbooks/*.md` gives 27 that **are** defined and **16** that are not.
One of the sixteen, `MetricsQueryBudgetTest`, is a PHP test class named in prose
(`monitoring-blind.md:34`) and is not an alert name at all.

**Fifteen.** Exactly the audit's figure.

## The fifteen are not one defect, and one remedy will be wrong for most of them

This is the part the round must get right. At least three distinct cases are
mixed together:

- **`QueueBacklog` is a truncation, not an invention.**
  `prometheus/rules/platform.yml:232` and `:255` define `QueueBacklogGrowing`
  and `QueueBacklogSevere`, and `alertmanager.yml:129,131,196` route both. The
  runbook names a prefix of two real alerts. That is arguably the most
  dangerous entry in the table: an operator greps the rules for `QueueBacklog`,
  gets two hits with *different thresholds and different routing*, and the page
  does not say which one they are holding. The remedy is a corrected reference,
  not a new rule.
- **Some describe conditions the platform genuinely does not alert on** —
  `MetricsCollectorDown`/`Slow` are the monitoring-blind case, and F-37 records
  that the collector registry was once absent entirely and every rule over it
  was silent. There the remedy may be to write the rule.
- **Some may be obsolete names** for alerts that were renamed. Check `git log`
  on the rules directory before writing anything: a rule that was renamed wants
  its runbook updated, and a round that adds a *new* rule under the old name
  ships two alerts for one condition.

Decide per name, and record the decision per name. "Fifteen missing rules, wrote
fifteen rules" would be the wrong outcome and it would look like success.

## A second, separate discrepancy this trace turned up

`docs/runbooks/README.md` states, three times, that there are **55** alerts:
*"The 55 alerts that predate this phase use `runbook_url`"*, *"37 of the 55
alerts now name a runbook in this repository. Eighteen do not"*. 37 + 18 = 55,
so the document is internally consistent — and the rules directory defines
**64**. The README is stale by nine, and its arithmetic being self-consistent is
precisely why nobody noticed.

This is inside F-39's own subject (the runbook/rule reconciliation) and is
**not** a new finding — do not number it. Fix it in the same round, and fix it
by **deriving** the number rather than editing 55 to 64: a hand-written count in
prose is what produced this defect and re-writing it by hand reproduces it.

`infrastructure/scripts/validate-monitoring.py` already fails the build for an
alert whose `runbook` path does not resolve — it checks rules → runbooks. F-39
is the **reverse** direction and nothing checks it. That reverse gate, not the
fifteen edits, is the closure: a check that every alert-shaped name cited in a
runbook resolves to a defined alert. It has to tolerate prose like
`MetricsQueryBudgetTest`, so the rule for what counts as a citation must be
stated in the gate and not left to a regex nobody can explain at 4am.
