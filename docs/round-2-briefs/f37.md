# F-37 — dedicated power operations are invisible to monitoring, and a stale claim poisons its idempotency key forever

**Audit text:** *"`F-37` Dedicated power operations are invisible to monitoring
and a stale claim poisons its idempotency key forever."*

Traced read-only on `claude/relaxed-turing-nh8ybf` at `d822de0`. **Both limbs
confirmed. The second is exact — "forever" is the right word — and the first
needs narrowing before it is true.**

## Limb 2 — the stale claim. Confirmed, and it is a real trap

`ChangeDedicatedServerPower::claim()`
(`src/Modules/Dedicated/Application/Actions/ChangeDedicatedServerPower.php:284-327`)
inserts the claim row in **its own transaction**, with outcome
`PowerOperationOutcome::Claimed`, and returns. On a unique-key collision it
reads the existing row and:

```php
if (! $existing->outcome->isSettled()) {
    throw DedicatedOperationRefusedException::becauseTheSameRequestIsStillInFlight(...);
}
```

`PowerOperationOutcome::isSettled()` is `return $this !== self::Claimed;`
(`Domain/Enums/PowerOperationOutcome.php:41-44`).

So the exit from `Claimed` is `settle()`, called on three paths further down
(`:227` indeterminate, `:237` refused, `:269` accepted). If the process dies
between the claim insert and any of them — deploy, OOM, worker restart, a
`SIGKILL` mid-BMC-call — the row stays `Claimed`. **There is no timeout, no
sweeper, and no operator path out of it.** Every later request carrying that
idempotency key is refused with "the same request is still in flight", for the
life of the row.

Two details that make this worse than a race you could shrug at:

- The claim is committed in **its own** transaction, on purpose (the docblock
  at `:292-300` explains why: a constraint violation poisons the enclosing
  PostgreSQL transaction). That commit is what makes the crash window real
  rather than theoretical — a claim written inside the outer transaction would
  roll back with it.
- The method's own `@throws` tag reads *"the winning request has not settled
  yet"*. The author modelled the concurrent case and only that case. The
  crashed case produces an identical row and an identical, permanent, refusal.

**Interlock: this is the same shape as F-34** (*"Timeout quarantines can never
be cleared; `ReleaseReason::OperatorAction` has no callers"*) — a state a
machine can enter and cannot leave. Read F-34's brief before designing the fix
and, if the two want the same mechanism (a bounded lifetime plus an audited
operator release), say so in your hand-back rather than building two.

## Limb 1 — "invisible to monitoring". True of power operations, false of
dedicated as a whole

Narrow it before you use it:

- There are **sixteen** collectors in
  `src/Modules/Monitoring/Application/Collectors/`. **None** reads
  `dedicated_power_operations`, `DedicatedPowerOperation` or
  `PowerOperationOutcome` — `grep -rn` over `src/Modules/Monitoring` returns
  nothing for any of the three.
- But dedicated is **not** wholly unmonitored: `ConsoleCollector.php:111-119`
  exports reinstall state per `DedicatedReinstallState` case under
  `['kind' => 'dedicated', …]`, and
  `infrastructure/monitoring/grafana/dashboards/dedicated.json` exists.

That combination is the argument for fixing it, not against. There is a
dashboard called *dedicated*, and an operator reading it has no cue that the
power path — the one that physically cycles a customer's machine — is absent
from it. In particular **`PowerOperationOutcome::Indeterminate`**, written at
`:227` when a BMC call times out, is a state the platform records and nothing
watches. An indeterminate power operation on a customer's dedicated server is
exactly the event that should page somebody.

## What closing this requires

- A collector (or an addition to an existing one) exporting power operations by
  outcome, with `Indeterminate` and stale `Claimed` distinguishable. Check
  `MonitoringServiceProvider` registration — the ledger records that this
  provider was once missing entirely and every rule read an absent series
  silently. **A new collector that is not registered fails exactly that way:
  green tests, no series, no alert.** Prove registration from the booted
  application, not from the file.
- A bounded lifetime for `Claimed` and a way out of it. Whatever is chosen must
  keep the property the table exists for: one intent reaches the chassis once.
  A naive "expire claims after N minutes" re-opens the double-send window the
  unique index was added to close — say explicitly how the fix avoids that.
- An alert rule only if a series exists to carry it, and a runbook if the rule
  points at one. See F-39: fifteen alert names are already cited in runbooks
  and defined nowhere, and this finding must not add a sixteenth.
- `REAL_INFRA_VERIFIED = NONE`. No BMC has been touched. A simulator-driven
  proof is the most this can have, and the hand-back must say so.
