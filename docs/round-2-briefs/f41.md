# F-41 — `phpunit.xml` pins that lose to any ambient variable, and a `migrate:fresh` with no guard

Round-1 audit, ARCHITECTURE_RISK:

> `phpunit.xml` pins ~30 environment variables without `force="true"`, so every
> one of them — `CACHE_STORE`, `QUEUE_CONNECTION`, `DB_DATABASE`,
> `BCRYPT_ROUNDS`, the six fake-provider pins — loses to any ambient variable.
> Reproduced: one exported variable flips a security test 3/3 pass → 3/3 fail.
> `RefreshDatabase` then runs `migrate:fresh` with no safe-database guard,
> while `WorkerHarness` enforces four.

Traced read-only. Confirmed, with the counts made exact and the mechanism read
out of the PHPUnit source rather than recalled.

## READ THIS FIRST — you can break twelve other agents with this finding

**The absence of `force="true"` is currently load-bearing for this entire
remediation programme.** Thirteen concurrent worktrees are isolated from each
other by setting `DB_DATABASE=lynomia_test_<slug>` as an ambient variable, which
works *only* because `phpunit.xml`'s pin yields to it. `scratchpad/mkworktree.sh`
says so in as many words and tells the reader to re-check the script when F-41
closes.

So: **a blanket `force="true"` on every entry is not a fix, it is an outage.**
At integration it would point every worktree at `lynomia_test`, and since
`RefreshDatabase` runs `migrate:fresh`, the first two agents to run would drop
the schema under each other — which is precisely the corruption three agents in
this programme have already suffered by a different route.

That does not make the finding invalid. It makes it a **per-variable decision
with a stated rule**, which is the actual work.

## What is there, exactly

`apps/control-plane/phpunit.xml`, `<php>` block: **32 `<env>` entries, none with
`force`.** (The audit says "~30"; the number is 32. Count it yourself.)

From `vendor/phpunit/phpunit/src/TextUI/Configuration/PhpHandler.php`, lines
138–146 — read, not remembered:

```php
$force = $variable->force();
if ($force || getenv($name) === false) {
    putenv("{$name}={$value}");
}
$value = getenv($name);
if ($force || !isset($_ENV[$name])) { ... }
```

So without `force` the pin applies **only when the variable is absent**, and
when it does not apply, `$_ENV` receives the *ambient* value. Exactly as stated.

### There is a second door, and a fix in `phpunit.xml` alone may or may not need it

`apps/control-plane/.env.testing` pins **24 of the same variables again**,
including `DB_DATABASE=lynomia_test` and all six fake providers. Laravel loads
it under `APP_ENV=testing`, and Dotenv does not overwrite an existing variable.

Work out the precedence yourself and write it down, because the answer decides
whether `.env.testing` needs touching at all: `phpunit.xml` is applied at
PHPUnit bootstrap, *before* Laravel boots, so by the time Dotenv runs the
variable is already set and Dotenv is a no-op for it. If that reasoning holds,
forcing in `phpunit.xml` is sufficient for those 24 and `.env.testing` is
irrelevant to them — but **verify it, do not accept my sketch of it.** Note that
`.env.testing` is copied into every worktree by `mkworktree.sh`, so its
behaviour is part of the isolation scheme too.

Note also that **`REDIS_DB` is in neither file.** It reaches
`WorkerHarness::redisDatabase()` from the ambient environment only, with a
fallback to the constant 15. So Redis isolation is unaffected by anything you
do here — but say so explicitly rather than leaving it to be inferred.

## The second half, which is the more serious one

`tests/TestCase.php` is **24 lines** and contains no database guard of any kind
— it sets an `Origin` header and nothing else. **260 test files use
`RefreshDatabase`**, and `RefreshDatabase` runs `migrate:fresh`, which drops
every table in whatever `DB_DATABASE` resolves to.

`tests/Feature/Queue/WorkerHarness.php` refuses, with a `RuntimeException` and
a message naming the database, unless **four** conditions hold: the environment
is `testing`; (read the file for the second); the database is the configured
test database; and the name itself says it is a test database. Its docblock
explains each, including the case it is really afraid of — a copy of a config
that was never repointed, naming a database full of real rows.

**State the asymmetry plainly, because it is the finding:** the harness that
*truncates* checks four times. The trait that *drops the schema* checks zero
times, and it is used by 260 files. The less destructive operation is the
guarded one.

This half is **independent of `force`**. Even with `DB_DATABASE` forced, an
operator or agent who sets it deliberately — as this programme does, thirteen
times over — gets no guard at all. Fixing only the `force` half leaves the
loaded gun on the table.

   a security test 3/3 → 3/3 fail. Find which test and which variable, and show
   it. Do not take my word or the audit's; the first-fail proof is the point.
2. **Classify all 32 pins** into: must never yield (a wrong value is unsafe or
   makes the suite meaningless — the six `*_PROVIDER=fake` pins are the obvious
   head of this list; `DB_CONNECTION`, `CACHE_STORE`, `QUEUE_CONNECTION`,
   `BCRYPT_ROUNDS`, `MAIL_MAILER`, `SESSION_DRIVER` are candidates), must remain
   yielding (`DB_DATABASE`, for the reason above — and say whether anything else
   belongs here), and don't-care. **Write the rule that decides the classes**,
   not just the resulting list; a list is a closed quantifier and this programme
   has rejected several.
   Note the `LEGAL_*` four have a stated reason to be overridable: the comment
   says "the tests that prove the fail-closed behaviour unset these for
   themselves." Check whether `force` interferes with a test unsetting a
   variable at runtime — it should not, but verify rather than assume.
3. **Give `RefreshDatabase` the guard `WorkerHarness` already has.** Same four
   conditions, same `RuntimeException`-not-skip discipline, applied once
   globally rather than 260 times. `tests/TestCase.php` is the obvious home;
   satisfy yourself that every `RefreshDatabase` user actually extends it, and
   report the number rather than assuming.
4. **Pin all of it.** What test fails if someone removes a `force` attribute, or
   deletes the guard? A fix no test can distinguish from its absence is not a
   fix. For the guard, the test is straightforward: point it at a
   non-test-looking database name and assert the refusal.
