# F-40 — the agent instructions claim a boundary the test does not enforce

Round-1 audit:

> 542 cross-module `Infrastructure` imports against a `CLAUDE.md` claim that
> the rule is enforced; only the `Http` half is.

Traced read-only. **Confirmed, and the shape of the fix is the opposite of the
obvious one.** Re-measure everything below; my trace is a starting point.

## The sentence

`apps/control-plane/AGENTS.md:26-29`, and `CLAUDE.md` byte-identical to it
(5,071 bytes each; `TheAgentInstructionsDescribeThisRepositoryTest` keeps them
so, and that test is real — *"They are one document under two names"*):

> A module never reaches into another module's `Infrastructure` or `Http`;
> cross-module work goes through the other module's `Domain` contracts or
> `Application` actions. `tests/Architecture/LayeringTest` enforces this,
> including references in docblocks.

## What is enforced, and what the test says about itself

`LayeringTest::no_module_calls_another_modules_http_layer` matches
`/^Lynomia\\Modules\\(\w+)\\Http\\/` and nothing else. **Only the `Http` half.**

And the test is *not* silently incomplete — read its docblock before you touch
anything, because it settles most of this finding:

> This is the module boundary that is actually real here.
>
> The stricter rule — a module may only use another module's Domain — is not
> the architecture this codebase has, and it is not obviously the one it should
> have: Orders genuinely needs Catalog's `Plan` model to price a line, and
> routing that through a DTO would add a layer whose only job is to be a layer.
> **Asserting it would leave a permanently red test, which teaches people to
> ignore red tests.**
>
> What must never happen is a module reaching another module's HTTP surface. A
> controller is the answer to "what does a customer's request look like", not
> "how do I get an invoice" …

**So the code is honest and well reasoned; the document is false.** This is the
same class as F-22's `config/logging.php` sentence: a document asserting an
enforcement that does not exist.

The audit says 542. **Neither figure is wrong until its extraction is named** —

Recount it yourself and **say how you counted** in the same sentence as the
number. This programme has been bitten repeatedly by figures whose subject was
never stated.

One trap in the counting, which bit me: **there is a module literally named
`Infrastructure`**, so a naive count conflates "the Infrastructure module" with
"another module's Infrastructure layer". My top pair reads
`Infrastructure -> Compute` (35), which means the module named Infrastructure
importing Compute's Infrastructure layer. Say which you are counting.

## What the round should do

The naive fix — enforce the stricter rule — would produce **exactly the
permanently red test the codebase deliberately declined to write**, and the
reasoning for declining it is written down and is good. Do not do that without
an argument that beats the one already in the file.

So, in order:

1. **Correct the document.** The sentence must say what is true: a module never
   reaches another module's `Http`, that is enforced by
   `LayeringTest::no_module_calls_another_modules_http_layer`, and reaching
   another module's `Infrastructure` is common today (give the count and the
   extraction) and is deliberately not asserted for the reason the test states.
   Both files, since they are one document under two names.
2. **Check the docblock claim separately.** The sentence says the rule is
   enforced *"including references in docblocks"*. Does the Http rule actually
   read docblocks? `importsIn()` is what decides. If it does not, that is a
   second false clause in the same sentence, and it is the more interesting one
   because a docblock reference is exactly how a boundary gets crossed
   invisibly. Measure it: plant a docblock `{@see \Lynomia\Modules\X\Http\Y}`
   in another module and see whether the test goes red.
3. **Then decide whether anything should be enforced about `Infrastructure`.**
   A defensible middle exists and is worth considering rather than assuming:
   pin the *count* so it cannot grow silently, or forbid the subset that is
   genuinely indefensible (another module's *notifications*, *factories* or
   *provider adapters*, as opposed to its Eloquent models) while leaving the
   model access the test's docblock defends. If you propose one, pin it with a
   mutation and show the number of existing violations it admits — a rule that
   is red on arrival is the thing the file warns against.
4. Whatever you write, **do not let the fix be "the document now hedges"**. A
   sentence that says "mostly enforced" is worse than the false one, because it
   cannot be checked. Say what is enforced, by which test, and what is not.
