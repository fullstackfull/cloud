# F-45 — the WordPress admin password is destroyed before the installer sees it

**Audit text:** *"WordPress admin password redacted before it reaches the
installer, which receives the literal `[redacted]`; the guarding test inspects
column names, not values. Out of approved launch scope and latent."* — TEST_GAP.

Traced read-only in the main checkout at `5cccd55`. **The audit is right about
the symptom and its framing is shallower than the defect.** The whole chain
below is confirmed by reading; re-derive it rather than carrying my line
numbers.

## The chain, end to end

1. `InstallWordPressOnceTheAccountExists.php:135` writes
   `'admin_password' => Str::password(24)` into a `ProvisioningJobRequest`
   payload — with a comment justifying the *strength* of the password, which is
   the one property that turns out not to matter.
2. That payload is persisted on `provisioning_jobs.payload`, and
   `ProvisioningJob::casts()` line 85 declares
   `'payload' => RedactedJsonCast::class`.
3. `SecretRedactor::isSecretKey()` matches by **substring** —
   `str_contains($normalised, $secret)` at line 186 — and `'password'` is in
   `config/security.php`'s `redacted_keys`. So `admin_password` matches, and
   line 97 replaces the value with `SecretRedactor::PLACEHOLDER`, the ten
   characters `[redacted]`.
4. `InstallWordPressHandler.php:171` reads
   `adminPassword: (string) ($payload['admin_password'] ?? '')`.
5. WordPress is installed with the admin password `[redacted]`.

A publicly-known ten-character password on a live customer site. It is latent
only because WordPress is `prepared` rather than `complete` and the path is not
sellable — **which is a fact about the launch scope, not about the code.**

## The reframe, and it is the whole brief

**The cast is behaving exactly as designed and exactly as documented. The
defect is in the listener, and the false sentence is in the cast.**

`RedactedJsonCast`'s own class docblock says:

> A credential must never be persisted in order to be sent to a provider:
> passwords are generated at execution time and delivered out of band. If one
> is put in the payload anyway, this is where it stops — the handler receives
> `"[redacted]"`, **which fails loudly**, instead of the platform quietly
> keeping a customer's root password in a table half the support team can read.

And `WordPressInstallRequest`'s docblock says:

> `$adminPassword` passes through and is never persisted. The platform
> generates it, hands it to the installer, and shows it to the customer once.

Both describe the same architecture: **generate at execution time, deliver out
of band, never persist.** The listener violates it by generating at *dispatch*
time and putting the result in a persisted payload. The cast then does precisely
what it promises to do — stop it.

**But "which fails loudly" is false.** It fails silently. Nothing checks, and a
site gets installed. Under the two questions in
`docs/round-2-briefs/adjudication-rule.md`: the code does not satisfy that
claim, and loud failure is achievable — so the code moves.

That is a sharper statement than the audit's, and it tells you where the fix
goes. The audit's *"the guarding test inspects column names, not values"* is
true and is a consequence rather than the cause: there was nothing in the
simulator to inspect a value against, which is F-24 limb 3's subject.

## What the round must establish before it fixes anything

**There is no out-of-band delivery surface.** `grep` for `showOnce`,
`show_once`, `revealOnce`, `one_time_secret`, `OneTimeSecret` and
`credential_delivery` across `src/` and `app/` returns **nothing**. So the DTO's
*"shows it to the customer once"* describes a capability that does not exist.

Establish that for yourself, and then take it seriously, because it constrains
the fix. Generating the password at execution time inside the handler satisfies
both docblocks and means the credential is never persisted — and it also means
the credential goes **nowhere the customer can reach**, which is a different
failure for the same customer.

**Building a one-time credential surface is new customer-facing capability and
is outside this round.** Do not build it. If the fix needs it, say so in those
words and propose rather than assume; that is a legitimate outcome and is how
several findings in this programme have correctly ended.

## The two candidate fixes, and they are not exclusive

- **(a) Generate at execution time.** Move the `Str::password(24)` out of the
  listener's payload and into the handler, so the credential exists only in
  memory on the execution path. This is the architecture both docblocks already
  describe. It is also what makes the cast's sentence true again.
- **(b) Make the promised loud failure real.** A guard in the handler that
  refuses a credential equal to `SecretRedactor::PLACEHOLDER`, or empty. This
  is what the cast's docblock claims already happens.

My reading is that (a) is the fix and (b) is the gate, and that shipping (a)
without (b) leaves the false sentence true-by-luck — nothing would stop the next
listener from putting a credential in a payload again. But argue it; if you
conclude only one belongs, say which and why.

**F-24's limb 3 has already built the detector for (b)** in the simulator:
`FakeHostingProvider` now refuses a credential that is empty or equal to the
placeholder, with a written rationale and a "WHAT THIS IS NOT" heading
disclaiming fidelity to any real panel. Read it before you write (b). It is on
`remediation/f24a` at `dba5965` — read it with `git show`, do **not** check that
branch out and do **not** import from it.

## The interlock, which is now the reason this finding is urgent

**Eight of F-24's fifteen deliberate reds are gated on F-45**, and F-24 is
CLOSED with a branch that is red by design and therefore not independently
mergeable. So this finding is the gate on another finding's integration. The
eight are one end-to-end WordPress order that demonstrates the defect live
through the production listener with no fixture involved, six
`TheWholeLifeOfAWordPressSiteTest` cases, and one whose payload has no
`admin_password` key at all — a fixture omission with no owning finding, which
is nonetheless blocked behind F-45 because adding the key sends it straight
through the cast.

**Check each of the eight against your fix.** If some do not clear, say which
and why — that is a result, not a failure.

## The mechanism is wider than the finding's own sentence

F-45's row is scoped to WordPress. The mechanism is not: `str_contains` against
`'password'` eats `admin_password`, `password`, `root_password`, `bmc_password`
and anything else carrying the substring, and `redacted_keys` holds twenty-nine
entries matched the same way.

**Census every persisted payload in the tree for a credential written into it.**
That is inside F-45's own sentence — the finding is a credential destroyed
before use, not a WordPress feature — so it is **not** a new finding and you
must not number it. If you find others, report them per site with the same
red-then-green evidence, or report that WordPress is the only one.

## §19, and it is absolute

**Never promote WordPress merely to eliminate the finding.** `Product::softwareState()`
must not move, `ProductSellability` must not move, and nothing you do may touch
`REAL_HOSTING_VERIFIED`, `REAL_INFRA_VERIFIED`, `REAL_PAYMENT_VERIFIED`,
`REAL_REGISTRAR_VERIFIED` or `READY_TO_SELL`, all of which are `NONE`. A fixed
install path is still an unsold product. If your change makes anything read as
more launch-ready than it was, you have done the wrong thing.

## Proof obligations

- **Red first.** A test that installs WordPress through the production listener
  and asserts the installer receives a usable credential must **fail against
  the current tree for the right reason** — the literal `[redacted]` arriving at
  the installer — before it passes. A test green on both sides has proved that
  the credential is still being destroyed.
- **§27 with force.** This is a TEST_GAP finding and the temptation is to adjust
  the expectation to the behaviour. If you relax an assertion, stop and write
  down why.
- **The guarding test the audit names** inspects column names rather than
  values. Find it, and fix what it asserts — but do not delete it; a column-name
  assertion is still a real property (no credential column exists), it is just
  not the one its name promises.
- Nothing here moves a `REAL_*` status. Say so in your hand-back.
