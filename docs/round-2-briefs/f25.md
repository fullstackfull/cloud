# F-25 — `ProductKind`, and the containment the audit says is an accident

Round-1 audit, ARCHITECTURE_RISK:

> `ProductKind` carries no docblock and is pinned by none of the 27
> architecture tests. The Prepared-product containment six auditors upheld
> rests on `Product::from()` throwing a `ValueError` — an accident, not a
> designed refusal. One added case silently sells a Prepared product.

**Traced read-only, and the finding has to be restated. One of its four claims
is now false, two stand, and the fourth has a different failure mode than the
one written.** Re-measure all of it; my trace is a starting point, not a
citation.

## What is actually there

Two enums, deliberately distinct, and the distinction is documented:

- `Catalog/Domain/Enums/ProductKind` — **3 cases**: `Vps`, `Dedicated`,
  `SharedHosting`. What has a price.
- `ProductReadiness/Domain/Enums/Product` — **12 cases**: the three above plus
  `WordPress`, `Domains`, `Dns`, `Backups`, and five marked *Prepared by the
  scope addendum*: `Cdn`, `ObjectStorage`, `GpuCompute`, `EmailHosting`,
  `ManagedKubernetes`. What has to work.

They are joined by value in two live places, both unguarded:

    ProductSellability::sellableCatalogueKinds():132   Product::from($kind->value)
    OrderPricing:143                                    Product::from($plan->product->kind->value)

(`InfrastructurePreflightService:337` uses `tryFrom`, so it is safe.)

## Claim 1 — "one added case silently sells a Prepared product": **FALSE today**

`ProductSellability::maySell()` opens with, before anything else:

```php
if ($product->softwareState() !== ProductSoftwareState::Complete) {
    return $this->rehearsal->includes($product);
}
```

and `PreparedProductRehearsal::includes()` opens with:

```php
if ($this->app->environment('production')) { return false; }
```

So a Prepared product is refused **in production, in staging and in a rehearsal
alike**, before `enforced()` and before the readiness row is read. Adding
`case Cdn = 'cdn'` to `ProductKind` would put it through `maySell(Product::Cdn)`,
which returns false in production. **It would not be sold.**

The docblock says why the ordering is deliberate, and the reasoning is good:
*"the environment exemption exists so a controlled provider can rehearse a sale
that production would refuse for want of a credential; it was never meant to
let a product with no real adapter be sold anywhere"*, and *"`ready_to_sell` is
a person's statement about providers, not a licence to sell software that does
not exist."*

**Read that gate before you touch anything.** The audit was written against a
tree that predates it — the `Product` enum's own docblock names the *"Gap 8
truth-closure patch"* as what introduced the software-state question. Your
first job is to confirm that reading and **say so plainly**, because a finding
that has been overtaken by a later patch should be recorded as such, not
rebuilt into a different finding to justify the row.

## Claim 2 — "rests on `Product::from()` throwing a `ValueError`": **no longer**, but the throw is still live and is now a different defect

Containment no longer rests on the throw. But the throw is still reachable, and
nothing anywhere in `src/` catches a `ValueError` — grep returns zero.

So a `ProductKind` case added with **no `Product` counterpart at all** (say
`case Colocation = 'colocation'`) does not silently sell anything. It throws an
uncaught `ValueError` out of `sellableCatalogueKinds()` — which runs on the
**catalogue listing in production** — and out of `OrderPricing`. That is a 500
on a customer-facing page, from adding one enum case.

Failing loudly beats failing silently, so this is the safe direction. It is
still worth deciding on rather than leaving to chance: the question for the
round is whether an unmatched kind should be a **startup/architecture refusal**
(a test that fails the build) rather than a runtime `ValueError` on a live page.

## Claim 3 — "pinned by none of the architecture tests": **TRUE**

`grep -rln ProductKind tests/Architecture/` returns nothing, against **28**
architecture test files. No test anywhere asserts the `ProductKind` ↔ `Product`
correspondence in either direction. The two places that rely on it are the two
`Product::from()` calls above.

**This is the real finding and it is the one to fix.** The correspondence is an
invariant that two live code paths depend on, held by nothing.

## Claim 4 — "carries no docblock": **TRUE**

`ProductKind` has no class-level docblock at all. Its only documented member is
`isAutomaticallyProvisioned()`. Its sibling `Product` has a substantial one
explaining exactly why the two lists differ — *"the catalogue lists what has a
price, and this lists what has to WORK"* — and that sentence is the thing a
reader of `ProductKind` most needs and cannot see from there.

## What the round should do

1. **Confirm or refute claim 1 by driving it**, not by reading. Add a case to
   `ProductKind` in a scratch tree, resolve it through `sellableCatalogueKinds()`
   in a production-like environment, and record what happens. Then remove it.
   Report the result whichever way it falls.
2. **Pin the correspondence.** An architecture test asserting that every
   `ProductKind` case has a `Product` of the same value — and deciding, with an
   argument, whether the reverse direction matters (it does not today: `Product`
   has nine cases with no kind, by design). Make it fail by adding a case.
3. **Decide what an unmatched kind should do** and implement that decision.
   A build-time refusal is the obvious candidate; if you keep the runtime
   `ValueError`, say why a 500 on the catalogue is the right answer.
4. **Give `ProductKind` a docblock** that says what it is and how it relates to
   `Product`, and cross-references it. Do not restate `Product`'s docblock;
   point at it.
5. If your measurement confirms claim 1 is false, **say so in the hand-back in
   those words**, with the evidence. The ledger will record F-25 as narrowed by
   measurement rather than quietly re-scoped.

## One warning

The tempting move here is to treat the audit's sentence as the specification
and build something that makes it true. It is not the specification; the
repository is. If the containment is real, the finding is a test gap and a
missing docblock, and that is a smaller and more honest closure than inventing
a sale that cannot happen.
