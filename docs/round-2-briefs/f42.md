# F-42 — the `apps/web` vitest suite is load-triggered flaky, and it is a required CI gate

Round-1 audit:

> The `apps/web` vitest suite is load-triggered flaky (required CI gate,
> `retries: 0`, no configured `testTimeout`; 3 of 4 parallel runs red on one
> commit, 0 red serial).

Traced read-only. **Every configuration claim is confirmed**, and since the
audit two independent remediation rounds have measured this suite extensively
on two different trees. You are starting with more evidence than most findings
here ever get. Re-measure anything you write down; the figures below name the
tree and the load they were taken on, and you must do the same.

## The configuration, confirmed

`apps/web/vitest.config.ts` merges `vite.config.ts` and adds exactly four keys:
`environment: 'jsdom'`, `globals: true`, `setupFiles: ['./src/test-setup.ts']`,
`css: false`.

There is **no `retry`**, **no `testTimeout`**, and **no pool or concurrency
setting**. So the suite runs on vitest's defaults: retry 0, a **5-second**
default test timeout, and full file parallelism.

CI runs it as a required step, `.github/workflows/ci.yml:191-192`:

    - name: Unit tests
      run: npm run test --workspace=apps/web -- --run

No `--no-file-parallelism`, no retries, no timeout override, on a shared runner.

## What two rounds measured, on two different trees

**Do not quote these against each other.** The branches have different
merge-bases — `remediation/f20` at `4c3344ea`, `remediation/f21` at `35baec5d`
— which is why one counts 488 tests and the other 502. Both are evidence about
the *failure mode*; neither is evidence about the other's tree.

| tree | load | invocation | result |
|---|---|---|---|
| f20 | 13.8 | `--no-file-parallelism --maxWorkers=1 --minWorkers=1` | **86 files / 488 tests, EXIT=0**, clean |
| f20 | ~13 | default (4 workers) | 10 failed / 478 passed; re-run of those 10 serially → 8 pass, other 2 pass individually |
| f21 | 14.4 | default | 3 failed / 499 passed; **a different 3 files** on the next run |
| f21 | 14.4 | `--no-file-parallelism` | 1 failed / 501 passed |

**The signature is the finding.** Across f20's ten failing files there were
**zero `AssertionError`** — eight `TestingLibraryElementError` and four `Test
timed out`, all element-not-found after an async wait. f21's lone serial
failure is a `findBy` element-not-found on a `role="link"` query. Two
independent trees, same family.

**And the datum that breaks the concurrency framing:** f21's lone failure,
`an-unverified-customer.test.tsx`, **fails 1 in 5 when it is the only file in
the run, serially.** So it is not suite concurrency. It is machine load
reaching a single test in isolation, against a 5-second default timeout.

An assertion failure in this suite would therefore be real and should stop a
round. A timeout or an element-not-found is what the environment produces.

## A hypothesis to test, not a conclusion to implement

`src/i18n/index.ts:71` initialises i18next as:

```ts
void i18n.use(initReactI18next).init({ resources: {...}, lng: detectLocale(), ... })
```

The `void` discards the promise. `init()` is asynchronous even with inline
resources, and **`src/test-setup.ts` does not wait for it** — it polyfills
`<dialog>` and nothing else. So a test that renders a component and immediately
queries for translated text can race initialisation, and `react-i18next` will
render the key or nothing until ready. A `role="link"` query matches on the
accessible name, which comes from a translation.

That would explain a failure that is load-sensitive, mode-consistent, and
reproducible on a single file in isolation. **Test it. Do not assume it.** The
honest outcomes are: it is the cause and awaiting init in `test-setup.ts` fixes
it; it is a contributing cause; or it is not the cause and the timeouts are
something else. All three are useful; only a measured one is worth writing.

## What the round has to decide, and the trap in it

The obvious fixes are `retry: 1` and a longer `testTimeout`. **Both make the
symptom go away without touching the cause, and one of them is dangerous.**

- A retry turns a genuinely broken test green on the second attempt. This
  programme's standard is that a test which cannot distinguish a working tree
  from a broken one is not a test. If you add retries, you must say what you
  have given up and how a real regression would still be caught.
- A longer timeout is more defensible — a 5-second default on a loaded CI
  runner is simply too tight for `findBy` — but it is still treating the clock
  rather than the race, and it will need raising again.
- Pinning worker count trades wall-clock for stability and does not touch the
  isolated-file failure at all, which the f21 measurement shows is real.

So: find the cause first. If the cause is the unawaited init, fix that and then
decide whether any of the three knobs is still wanted. Whatever you choose,
the deliverable is **a measurement showing the failure mode is gone under the
load it appeared at**, not a green run in a quiet window.

## How to measure this honestly

- **State the load average beside every figure.** A frontend figure without a
  load is not a measurement here — that is a correction I had to make to my own
  earlier guidance, recorded in the ledger.
- Run each configuration several times. A single green run at load 3 proves
  nothing about a CI runner.
- Reproduce a failure before you fix anything. `an-unverified-customer.test.tsx`
  alone, serially, repeated — f21 got 1 in 5.
- After a fix, re-run the same file the same way the same number of times, at a
  comparable load, and give both numerators.
