## Do the census before you write a line of production code

Produce, and hand back, a table with one row per declared notification type and
these columns:

| type | declared where | translated (en / ar) | produced by | reachable? |

Where **produced by** is a file and a line, or the word `nothing`. And where
**reachable** is the harder question and the one the row's word *"produced"*
glosses: a type produced only by a code path that no route, command, listener
or scheduled job can reach is not produced in any sense that matters, and a
type produced by a seeder or a test fixture is not produced at all.

State how you enumerated the declared set, and how you enumerated the
producers, and make both reproducible by a reader. If the two enumerations use
different definitions of "notification type" you will get a number that is not
comparable to sixteen, which is how this programme has produced three
irreconcilable counts of other things.

**Then say whether the number is sixteen.** If it is not, say so in those
words and give the current number with the delta attributed — how many were
wired by F-09/F-10, how many by something else, how many were never sixteen.

## What may and may not be repaired

- **Nothing already wired may be duplicated.** A second producer for a type
  that has one is a worse defect than the one you are fixing: customers get the
  notification twice and the duplicate is invisible in review.
- A type that is genuinely unreachable has **two honest dispositions**, and you
  choose per type with the reason written at the site: wire the producer, or
  **delete the type and its two translations**. Deleting is not defeat. A
  declared-and-unproduced notification is a promise the platform does not keep,
  and the repository already holds the argument for this in F-23's neighbours:
  a string that exists for a state nothing can enter reads as coverage and is
  silence.
- **Do not wire a producer you cannot reach from a test.** If wiring a type
  requires a provider call, a payment, a registrar or real infrastructure, it
  is out of scope by the standing constraints below, and the honest outcome is
  to say which types those are and leave them.
- **Nothing you do may move a launch status.** `Product::softwareState()`,
  `ProductSellability`, every `REAL_*` and `READY_TO_SELL` stay exactly where
  they are. If your change makes any surface read as more sellable than it was,
  you have done the wrong thing.

## The oracle, which is the point of the round

A census in a hand-back rots. The deliverable that does not is **a test that
fails when a type is declared and not produced**, in whichever direction you
settle on — and this programme's standing complaint applies: a hand-written
list of sixteen names is not that test, because the seventeenth type is covered
only if somebody remembers to add a line, and nothing notices if they do not.
`tests/Architecture/` holds the family this belongs to; read
`EveryControllerMethodIsReachableTest` and the two capability tests before you
write a new one, and say why yours is or is not one of them.

Say explicitly **what your oracle cannot see** — a producer reached only
dynamically, a type named through a variable, whatever it is. A boundary stated
is a boundary; a boundary implied is a claim of completeness.

## Mutation discipline, four obligations

1. Prove the edit landed (sha256 before and after, plus a whole-file
   `diff -u0`).
2. Prove it landed **where you meant** — anchor by string, never by line.
3. Prove it is behaviour-preserving except for the property under test.
4. **Restore against the value taken before, not against HEAD.**

And: **a harness that refuses to mutate must also refuse to run.** Self-test it
with a non-existent anchor first.

At minimum your oracle must die to: a new declared type with no producer; a
producer deleted from a type that has one; and a translation removed. Say which
assertion each kills.

## Proof standard

Three proofs, all three required:

- a JSON summary with **no `skipped` key** and `tests == passed`;
- `--log-junit`, with **every** `testsuite` element at `skipped="0"`;
- `ARTISAN-TEST EXIT=0` — take it with `${PIPESTATUS[0]}`, not `$?` after a
  pipe.

Run `./vendor/bin/pint --test` **at tree scope from `apps/control-plane`**,
which is CI's `working-directory`.

Test counts add across paths. **Assertion totals do not.**
