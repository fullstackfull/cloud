most useful fact about F-24 is not in the audit at all:

**Two of the eight simulators already implement, correctly and with a written
rationale, the exact pattern the third is missing.** This is not a finding
about an unknown provider contract — §24's "never invent a real provider

## Limb 1 — DNS record identity

**Status: confirmed, and worse than the audit says.**

`FakeDnsProvider.php:195`:

```php
$key = $record->type()->value.'|'.$record->name();
```

The record's **value is not in the key**. Consequences, all reachable:

- `publish()` of a second A record for the same name overwrites the first
  (`:204`), and — line `:202` — the survivor inherits the first record's id
  via `$held?->id()`. Two distinct records, one row, one id.
- `delete()` (`:217`) unsets by `(type, name)`. Deleting one A record of a
  round-robin set deletes the set.

This is the F-11 defect (`$existing[0]` collapse in the Cloudflare adapter)
reproduced in the oracle, exactly as the audit says.

**The consequence the audit does not draw, and the one that matters for
sequencing:** the fake is not merely *unable to catch* the adapter's bug — it
is unable to *hold* the correct behaviour. It physically cannot store two
records at one `(type, name)`. So a corrected Cloudflare adapter, tested
against this fake, **fails**. Any F-11 fix that does not also fix this fake is
either untestable or tested against an oracle that punishes the fix.

Check before you start: F-11 ran nine rounds; its last dispatched round was
cancelled. `git log --oneline -- src/Modules/Dns/Infrastructure/Providers/FakeDnsProvider.php`
showed no round-2 commit when I traced it. Re-check — if an F-11 round already
fixed the fake, limb 1 is closed by another finding and you say so with the sha
rather than doing it twice.

## Limb 2 — compute double-build

**Status: confirmed, verbatim.**

`FakeComputeProvider::createVirtualMachine`, `:150-156`:

```php
if (self::hostnameCarries($request->hostname, self::TIMEOUT_MARKER)) {
    throw ComputeProviderException::requestFailed(self::NAME, 'create_vm', [
        ...
    ], indeterminate: true);
}
```

— and the machine is registered at `:160`, four lines later. The exception is
flagged `indeterminate: true`, which is the fake *telling the caller* the
outcome is unknown, while its own state says with certainty that nothing was
built. A retry therefore always succeeds cleanly. The double-build cannot
happen in any test in this repository.

The same inversion holds in the other direction at `:366-374`: the
`UNDESTROYABLE_MARKER` throws `indeterminate: true` before `unset()`, so an
indeterminate destroy always means the machine survived. In both directions the
fake's state resolves the ambiguity in the convenient direction. That is the
one-sentence statement of this limb, and it is more precise than "throws before
registering".

Four markers exist (`:60,:63,:72,:82`); none produces a landed write with a
lost answer. Copy the registrar's shape, not a shape you invent.

## Limb 3 — hosting credentials

**Status: half wrong, half confirmed, and the confirmed half is live.**

*"never reads the domain"* — **false.** `createAccount` reads
`$request->primaryDomain`, stores it on the `RemoteAccount` (`:161`) and
returns it (`:174`). `installWordPress` reads and lowercases `$request->domain`
(`:423`). Do not carry this half of the sentence forward.

*"never reads the password"* — **true**, and deliberately, with a reason
written at `FakeHostingProvider.php:243-251`:

> Nothing is stored. The fake mirrors the real adapters here on purpose: a fake
> that kept passwords would make it possible to write a test that depends on
> the platform holding one.

That reason is sound and `CreateAccountRequest`'s docblock backs it. **Do not
make the fake store passwords.** The audit's *consequence* nevertheless
survives: neither `createAccount` nor `installWordPress` ever **inspects** the
password. `CreateAccountRequest::$password` and
`WordPressInstallRequest::$adminPassword` are plain `string`, unvalidated. An
empty password, or the literal `[redacted]`, is accepted and reported as
success.

The resolution that satisfies both the finding and the docblock is
**validate without retaining**: refuse an empty or obviously-redacted
credential the way a real panel refuses one, and store nothing. That is a
change of four lines and it is the only version of this limb I would defend.

**This is not hypothetical.** F-45 is the finding that a WordPress admin
password is redacted to the literal `[redacted]` before it reaches the
installer, and that its guarding test inspects column names rather than values.
Limb 3 is *why* that test had to be written that way: there was nothing in the
fake to inspect. Fixing limb 3 is the mechanism that makes F-45 testable.
Co-ordinate — do not fix F-45's symptom here, and note in your hand-back that
F-45's adjudication now has a tool it did not have.

## Limb 4 — the audit's scope is three, the tree's is eight

Five simulators the audit never names. Three of them (`FakeBackupProvider`,
`FakeDedicatedProvider`, `FakeReverseDnsProvider`) I did not trace. Trace them
or say plainly that you did not; do not let "the audit named three" become the
reason only three were looked at. This is inside F-24's own sentence — "the
provider simulators model the convenient case" is a claim about the
simulators, not about three of them — so it is **not** a new finding and you
must not number it as one.

## Limb 5 — the payment simulator cannot fail

`FakePaymentProvider::createPaymentIntent` (`:146-177`) has **no transport
failure path at all**. Every outcome is a returned status; the only throws in
the class are an unsupported currency (`:535`), an argument error (`:385`), and
three in the refund/webhook helpers. A charge created at the PSP while the HTTP
call dies — the one shape where a customer's money moves and the platform does
not know it — is unrepresentable.

**Do not treat this as established.** Two things could make it moot and I
checked neither: the webhook/reconciliation path may already cover the state
(the class exposes `record()` at `:437`, which lets a test drive any status
directly), and `REAL_PAYMENT_VERIFIED = NONE` means no real PSP has ever been
called. Establish or dismiss it with a reproduction before it enters the
ledger as anything but "raised and open".

## What closing this finding requires

Per §9 all eight steps, and per the standing rule you do not declare your own
closure. Specific to F-24:

1. **First-fail proof is the whole finding.** For each limb, the proof is a
   test that *fails against the current simulator for the right reason* and
   passes after. A test that passes both before and after has proved that the
   simulator is still convenient. Show the red.
2. **§27 applies with force here.** The temptation in a TEST_GAP finding is to
   adjust the test to the simulator. If you find yourself relaxing an
   assertion, stop and write down why.
3. **§24 does not license guessing, and does not need to.** For limbs 1–3 the
   correct behaviour is established in-tree: the registrar fake, the hosting
   fake's install path, and the Cloudflare/cPanel adapters' own docblocks. Cite
   the in-tree source for every behaviour you add. If a behaviour has no
   in-tree source, do not add it — record it as insufficient evidence.
4. **Nothing here may move a `REAL_*` status.** A simulator that models the
   dangerous case is still a simulator. Say so in your hand-back.
5. **Cross-finding**: F-11 (limb 1, may already be done), F-45 (limb 3, becomes
   testable), F-13 (the privilege map that only the simulator can satisfy — the
   same class, already its own finding; do not absorb it).
