# F-23 — the reachability suite covers five kinds of thing and not the two that carry state

Round-1 audit, TEST_GAP:

> The architecture suite enforces translations for states that cannot occur.
> It asserts reachability for methods, events, capabilities, metrics and
> translations — and for no enum case or state-machine state.

Traced read-only. **Confirmed, and there is a third thing the audit does not
mention which is probably the largest hole.** Re-measure everything.

## The suite, enumerated

`tests/Architecture/` holds **28** files (the audit says 27; the count has
moved, so say which you counted and when). The reachability family is real and
thorough for what it covers:

| kind | test |
|---|---|
| controller methods | `EveryControllerMethodIsReachableTest`, `NoDeadMethodsTest` |
| domain events | `EveryDomainEventIsConsumedTest` |
| capabilities | `EveryDeclaredCapabilityHasAConsumerTest`, `NoDeadCapabilitiesTest`, `EveryPublishedCapabilityIsEnforcedTest` |
| metrics | `EveryAlertMetricHasAProducerTest`, `EveryBackupAlertMetricHasAProducerTest` |
| translations | `EveryMessageCodeIsTranslatedTest`, `EveryStateAScreenShowsIsTranslatedTest` |

There is **no** `Every…EnumCaseIsReachable` and **no** test that a state a
machine declares can actually be entered. Confirmed by reading the file list.

## The consequence the audit names

`EveryStateAScreenShowsIsTranslatedTest::every_value_a_screen_can_render_has_a_string_in_this_language`
walks `$enum::cases()` and requires a string for **every case**, in every
locale. A case that no transition can produce therefore still demands a
translation — in English and Arabic — and gets one. The suite is green, the
string exists, and nothing anywhere establishes that a customer can ever see
it. The test's companion, `no_string_names_a_state_that_no_enum_has`, closes
the reverse direction, so the pair is tight about strings and silent about
states.

## The third thing, and I think it is the biggest

**The enum list is hand-written.** The test imports its enums one by one at the
top of the file: **70** `use Lynomia\…\Enums\…` lines. Under `src` there are
**136** files matching `*/Domain/Enums/*.php`.

So a new enum is not covered unless somebody remembers to add a `use` line, and
nothing notices if they do not. That is the same shape as the eighteen
hand-written directory lists already recorded in this ledger's
"Discovered / out of scope" rows, and it makes the translation guarantee much
weaker than it reads.

**Do not take 70-of-136 as the gap.** Not every enum is screen-facing, and the
test is named for the ones that are. The number to produce is: *how many enums
are rendered to a screen and are absent from the list* — which needs a
definition of "rendered to a screen" that you state and defend before you
count. A count without that definition is exactly the kind of figure this
programme keeps retracting.

## What the round should do

1. **Derive the enum list instead of writing it.** Whatever rule you use — a
   marker interface, a directory convention, a `JsonSerializable` on the
   resource, a registry — the property to obtain is *"adding a screen-facing
   enum without a translation fails the build"*. Pin it by adding one and
   watching red.
2. **Assert reachability of enum cases**, at least for the state enums: for
   each case, is there a transition, a constructor, a factory or a query that
   can produce it? Where the answer is no, the case is either dead (delete it)
   or reachable by a path nobody has written down (document it, with the path).
   Both outcomes are worth more than the current silence.
3. **Then revisit the translations.** A case proved unreachable should not need
   a customer-facing string, and saying so in the test is the honest version of
   the audit's complaint.
