# F-43 — `ConsoleSessionStore::consume()` never compares `expires_at`

Round-1 audit:

> `ConsoleSessionStore::consume()` never compares `expires_at`, so its expiry
> tests prove `ArrayStore` and fail under the production driver.

Traced read-only. **The finding is exact**, and the mechanism is now pinned
from vendor source rather than from memory. One correction of emphasis is
below and you must carry it, because overstating this finding is the easiest
way to get the round rejected.

## What is there

`src/Modules/Vps/Application/Services/ConsoleSessionStore.php`.

`issue()` writes the record with `put(..., self::TTL_SECONDS)` and puts an
ISO-8601 `expires_at` **inside** the record.

`consume()` reads the record and, in order: refuses if it is not an array;
`hash_equals` on the token hash, deliberately **not** consuming on a wrong
token (the reason is good — the id travels in a URL and the token does not, so
burning on a wrong token would let anyone who can guess an id destroy permits
as fast as they are issued); then the atomic `add()` on the consumed marker;
then `forget()`; then it constructs the returned `ConsoleSession` with
`CarbonImmutable::parse((string) $record['expires_at'])`.

So `expires_at` is **written, read, and used only to populate a return value.**
It is never compared to anything. Expiry is delegated entirely to the cache TTL.

## Why the tests prove the store and not the code

Two tests assert expiry, both by moving Carbon's clock:

    tests/Feature/Console/AuthoriseConsoleConnectionTest.php:114
    tests/Feature/Vps/VpsConsoleEndpointTest.php:59
        $this->travel(ConsoleSessionStore::TTL_SECONDS + 1)->seconds();

`phpunit.xml:35` pins `CACHE_STORE=array`. From the vendor source in this tree:

    ArrayStore::get()   line 96:
        if ($expiresAt !== 0 && (Carbon::now()->getPreciseTimestamp(3) / 1000) >= $expiresAt)

    RedisStore::put()   line 135:
        $connection->setex($this->prefix.$key, (int) max(1, $seconds), ...)

`ArrayStore` decides expiry against **Carbon**, which `travel()` moves.
`RedisStore` hands the TTL to the Redis server, which uses **wall clock** and
which `travel()` cannot touch. So under the production driver the key is still
live after the travel, `consume()` has no `expires_at` comparison to fall back
on, and it **returns a valid session**. The test would fail, and it would fail
by discovering that the property it claims to guarantee is not implemented.

The store's own docblock is explicit that Redis is the production store:
*"The store must be shared between the API and the console gateway, which means
Redis in any real deployment."* So this is not a hypothetical driver.

## The correction you must carry

**Production is not currently broken, and you must not say it is.** In real
operation real time advances, Redis expires the key at sixty seconds, and the
permit is refused. The docblock's reasoning — *"Expiry that the store itself
enforces cannot fall behind"* — is sound and is a deliberate design choice, not
an oversight.

What is actually wrong is three things, and they are worth separating:

1. **The tests prove `ArrayStore`'s clock, not the code's behaviour.** Whatever
   else you do, a test that passes only because the test store shares Carbon's
   clock with the test is not evidence about the deployed system.
2. **A field is written and never read.** `expires_at` is in the record and
   nothing checks it. That is either dead weight or a missing check, and the
   code does not say which. Whichever it is, the repository should say so.
3. **There is no defence in depth behind the TTL.** The TTL is the only thing
   refusing an old permit. It is a good first line. It is also the *only* line,
   and the failure modes where it is wrong are real rather than exotic: a
   `put()` whose TTL is changed independently of `TTL_SECONDS`, a store whose
   TTL granularity differs (`max(1, $seconds)` in `RedisStore` already floors
   it), clock skew between the API host that computes `expires_at` and the
   Redis server that expires the key, or a future caller that writes the record
   by some other path.

## What the round has to do

Decide and implement, then argue for what you chose:

- **Compare `expires_at` in `consume()`**, returning null on an expired record
  exactly as it does for the other three refusal shapes — the docblock already
  says all four must be indistinguishable to the caller, and this would make
  that sentence true of four rather than three. This is the obvious fix and it
  is probably right, but say why it does not contradict the "cannot fall
  behind" reasoning: it does not replace the TTL, it stops trusting it alone.
- **Or delete `expires_at` from the stored record** and state that the TTL is
  the sole authority. Defensible, cheaper, and honest — but then the returned
  `ConsoleSession`'s `expiresAt` has to come from somewhere else, and you must
  check every consumer of that field before removing it.

Whichever you choose, **the tests must stop proving the store.** A test that
travels Carbon and asserts refusal is measuring `ArrayStore`. Options, and you
should say which you took and why:

- assert the refusal at the level `consume()` actually decides — construct the
  record with a past `expires_at` directly in the store, without travelling,
  so the code's own comparison is what refuses;
- and, separately, pin the claim about the store by asserting the TTL is passed
  to `put()`, which is a different fact and worth its own test.

**Do not** simply change the test to expect current behaviour. That is
explicitly not a closure under this programme's rules.
